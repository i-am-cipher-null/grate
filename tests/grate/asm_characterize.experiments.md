# Fragment hardware experiments (manifest-driven)

**Status.** Measured on hardware. Every word below was produced by
`asm_characterize.py` from the manifest named with it, three times per variant,
with the controls passing before and after the sweep. The raw evidence is the
`characterization/<name>-<timestamp>/` directory the runner leaves behind
(`results.tsv`, `logs/`, `metadata.json`), which is git-ignored.

**Scope.** Four features that a backend needs: the ALU addition-disable field,
the TEX coordinate register select, `alu_buffer_size`, and the MFU multiplier's
source select. The third grew into a
matrix and is generated by `tests/grate/asm/make_alu_buffer_matrix.py` rather
than written out by hand; its counts were the hardest thing in this collection to
get right, and one wrong pin of it is written up below as a trap. The runner
itself and the manifest format are in [asm_characterize.md](asm_characterize.md);
the environment variables and the traps are in `docs/hardware-testing.md` on the
`reverse-engineering` branch.

## Running them

From the repository root, with a build tree that has `tools/assembler`:

    GRATE_ASSEMBLER=$HOME/build/grate/tools/assembler \
        meson devenv -C ~/build/grate \
        python3 $PWD/tests/grate/asm_characterize.py \
        $PWD/tests/grate/asm_characterize.alu_add_disable.json

`meson devenv` changes the working directory to the build tree, so both paths
have to be absolute - a relative manifest path fails with
`No such file or directory: '<build>/tests/grate/...'`. The runner derives the
repository root from the script's own path, so the manifest and the `program`
stages it names still resolve against the source tree.

The seven `alu_buffer_*` manifests are generated. Regenerate one after changing
its test table, and pin its words only from a run whose repeats agreed:

    python3 tests/grate/asm/make_alu_buffer_matrix.py                    # matrix
    python3 tests/grate/asm/make_alu_buffer_matrix.py --mode ladder      # ladder
    python3 tests/grate/asm/make_alu_buffer_matrix.py --mode blocks      # group probes
    python3 tests/grate/asm/make_alu_buffer_matrix.py --mode xgroup      # two groups
    python3 tests/grate/asm/make_alu_buffer_matrix.py --mode arb         # two DWs
    python3 tests/grate/asm/make_alu_buffer_matrix.py --mode pseq        # two DWs, field swept
    python3 tests/grate/asm/make_alu_buffer_matrix.py --mode dwpos       # one DW, each position
    python3 tests/grate/asm/make_alu_buffer_matrix.py --results <run dir>

The MFU selector manifest is generated by its own script, which takes the same
`--results` argument for pinning:

    python3 tests/grate/asm/make_mfu_selector.py                         # source sweep
    python3 tests/grate/asm/make_mfu_selector.py --results <run dir>

Run one size at a time (`--sizes N --out /tmp/m_nN.json`) and pin the checked-in
manifest from those runs: a count that hangs wedges the channel for every later
variant in the same run, so a single combined sweep can turn one bad size into
four. `tests/grate/asm/results/` keeps the raw `results.tsv` of the runs quoted
below.

Each manifest runs two controls first, refuses to start the sweep if either
fails, and repeats the controls afterwards. A run is only counted when the
process exits 0 and prints exactly one `result 0x........` line whose value
matches `expected`, which every variant here carries.

Results below are from a Toshiba AC100 / Dynabook AZ (Tegra 20,
`7.2.0-gd1efa725955b`, armv7l). The matrix numbers are the count-matched rerun
(commit `071394e` plus the generator change that made the count equal to each
program's batch count); the earlier figures they replace are marked as such
where they would otherwise be read as current.

## 1. ALU addition disable: two multiplies per slot

`asm_characterize.alu_add_disable.json`, template
`asm/alu_add_disable.in`. The opcode is `MUL` - the parser sets ALU bit 59 from
the mnemonic, so the two spellings differ in one bit. Operand values are
`u0 = u1 = 0.5`, `u2 = 0.75`, and batch 1 prefills both fx10 halves of `r2` with
`0.5` (`0x7F`) so an unwritten half cannot be mistaken for a product. The DW
readback word is `r3.hi, r3.lo, r2.hi, r2.lo` from MSB, so one store shows both
halves of `r2`.

| variant | instruction | word |
|:--|:--|--:|
| `prefill-only` | `NOP` | `00007F7F` |
| `mad-three-operand-control` | `MAD r2.l*, u0, u1, u2` | `00007FFF` |
| `mul-low-mask` | `MUL r2.l*, u0, u1, u2` | `0000BF40` |
| `mul-high-mask` | `MUL r2.*h, u0, u1, u2` | `000040BF` |
| `mul-both-mask-fp20` | `MUL r2.lh, u0, u1, u2` | `0000E700` |
| `mul-rd-is-rb` | `MUL r2.l*, u0, u1, u2, rB` | `00006040` |
| `mul-rd-is-rc` | `MUL r2.l*, u0, u1, u2, rC` | `00008F40` |
| `mad-rd-is-rb-control` | `MAD r2.l*, u0, u1, u2, rB` | `00007F9F` |

Reading it:

* **the addend really is dropped.** `MAD` stores `0.25 + 0.75 = 1.0` (`FF` in
  the low byte); `MUL` with the same operands stores `0.25`, so bit 59 is not a
  formatting flag.
* **a single-half destination yields both products, and the mask bit chooses
  which half gets `rA*rB`.** `MUL r2.l*` writes `r2.lo = 0.25` and
  `r2.hi = 0.75`; `MUL r2.*h` writes `r2.hi = 0.25` and `r2.lo = 0.75`. That is
  the patent table in `docs/fragment-shader-isa.md` 5.13 measured exactly, and
  it is a
  trap for a backend: `.l*` does **not** mean "low half only" for `MUL`, so a
  value the allocator believes is live in the high half is destroyed.
* **the second product follows `rD`, not a fixed register.** `rB` gives
  `0.75 * 0.5 = 0.375` (`60`) and `rC` gives `0.75 * 0.75 = 0.5625` (`8F`),
  both landing in the half the mask did not name.
* **the fp20 (`.lh`) destination keeps one product.** It stores `0xE700`, which
  is `fp20` of `0.25` read back through the two fx10 halves - the second product
  is lost. So the 2-for-1 form exists only with a single-half mask.
* **`rD` is not a free operand.** The field is six bits (a register select plus
  modifiers), so `MAD r2.l*, u0, u1, u2, u3` is a parse error ("Invalid src
  register"); `rD` can only be `1.0`, `rB` or `rC`. With the usual omitted `rD`
  the second product is therefore `rC * 1.0`, i.e. `MUL r2.l*, a, b, c` copies
  `c` into the other half for free.

A backend that emits `MUL` must therefore either use a destination half it does
not need, or pair two products deliberately. The saving is one ALU slot per two
multiplies, out of the 256-slot budget.

## 2. TEX coordinate and destination register select

`asm_characterize.tex_register_select.json`, template
`asm/tex_src_select.in`, run with `--texture`. TEX bit 5 (destination) was
already measured; bit 4 (coordinates) was only written up. The harness's default
texture is 4x4 `RGBA8888` with columns 0..1 black and 2..3 white, so `S` alone
decides the colour, and the four row registers hold distinct fp20 values
`r0 = 0.05`, `r1 = 0.25`, `r2 = 0.75`, `r3 = 0.95`. Coordinates are written with
`.lh` (fp20); an fx10 coordinate half does not work.

| variant | TEX | reads `S` from | word |
|:--|:--|:--|--:|
| `src0-dst0` | `tex r0, r1, tex0, r0, r1, r2` | `r0 = 0.05` | `00000000` |
| `src0-dst1` | `tex r2, r3, tex0, r0, r1, r2` | `r0 = 0.05` | `00000000` |
| `src1-dst0` | `tex r0, r1, tex0, r2, r3, r0` | `r2 = 0.75` | `FFFFFFFF` |
| `src1-dst1` | `tex r2, r3, tex0, r2, r3, r0` | `r2 = 0.75` | `FFFFFFFF` |

* bit 4 selects the second coordinate group: `S,T,R = r2,r3,r0` instead of
  `r0,r1,r2`, and the sampled column moves from 0 (black) to 3 (white) while
  everything else in the program is unchanged;
* bit 5 is independent, so all four combinations are legal;
* `src1-dst1` samples *and* overwrites `r2`/`r3` in one instruction and still
  returns the white texel, so the read happens before the write.

The attribution is not only the colour: dumping the raw program shows the two
`src0`/`src1` programs differ in exactly one word, `[10] = 0x00000400` versus
`0x00000410`. Bit 4 is the only bit that moved.

What this buys a backend: the sample result can live in `r0`/`r1` while the
coordinates stay in `r2`/`r3`, which removes the copy into the pixel packet that
`filter_quad_fs` and `tex_cross_batch` otherwise need before every sample.

## 3. `alu_buffer_size`: what a later batch can actually see

The starting point was `asm_characterize.alu_buffer_rows.json` (template
`asm/alu_buf_three.in`): three batches, `r2.lo = 0.25`, then `r3.hi = 0.5`, then
a store. It returned `7F000040` at size 1 **and** at size 2, which the
per-batch row rule cannot produce: at size 2 the storing batch runs on row 0 and
should not see the row-1 write at all. The matrix below replaces that shape.

| variant | size | `0x520` | word |
|:--|--:|:--|--:|
| `size1-baseline` | 1 | `0x20006003` | `7F000040` |
| `size2-two-rows` | 2 | `0x20006006` | `7F000040` |
| `size3-documented-zero` | 3 | `0x20006009` | `00000000` |

(the fourth variant, the same shape at size 4, is gone: three batches are not a
whole number of four-batch groups and that program hung, see "Batch counts that
leave an incomplete group").

### The matrix

`asm/alu_buf_matrix.in` is a four-batch program, one ALU packet and one DW
operation per batch, both chosen per variant, so only the write and the store
move. Size 3 uses a six-batch template (`asm/alu_buf_matrix6.in`): four batches
cannot be split into groups of three, and an incomplete final group is not a
fair test of anything. `asm/make_alu_buffer_matrix.py` expands the table into
`asm_characterize.alu_buffer_matrix.json` (210 variants, sizes 1 to 4),
`..._ladder.json` (34, the batch-naming tests alone), `..._blocks.json` (12, the
eight- and six-batch group probes), `..._xgroup.json` (28, two complete groups
per variant) and `..._arb.json` (22, two DWs in one group), and pins their words
from a named run (`--results DIR`).

**Every program runs at a count equal to its own batch count**: 4 at sizes 1, 2
and 4, 6 at size 3. That is not a detail. The first version of this matrix poked
8, 9 and 8 at a four-batch program; since one count is one batch, sizes 2 to 4
ran their program twice, and a second pass starts from the rows the first pass
left. Both oddities recorded in that version - a write surviving into a later
group, and size 3 storing from batch 3 - are what a repeated program produces,
and neither survives the matched count.

Per buffer size the tests are a write x store grid (16 at four batches, 36 at
six), a *ladder* that gives every batch its own constant (4 or 6), a
store-in-every-batch form (2), two writes to one register in both orders (3 or 5
store positions, each way), two registers together in both orders (2), every
register half read at the group starts that actually fire (8 or 16) and an
untouched-row control first and last in the group (2).

Sentinels are chosen so the word names the write. `r2.lo` lands in bits 0..7,
`r2.hi` in 8..15, `r3.lo` in 16..23 and `r3.hi` in 24..31 of the result, and
`.l*` stores fx10, so batch 0 reads `0x10`, batch 1 `0x20`, batch 2 `0x40`,
batch 3 `0x60`, batch 4 `0x7F` and batch 5 `0x9F`. An untouched row reads
`0x00000000` at the first and the last store position that fires, so no value
below is leftover state. The control has to store where the DW runs: an earlier
version kept its store at batch 1, which starts a group only at size 1, so at
sizes 2 to 4 its zero meant "no store executed" rather than "a store read
cleared state". The two controls are now the first and last entry of
`store_positions()`, which is why they are named `-s0`/`-s2` at size 2 and
`-s0`/`-s3` at size 3; size 4 has one firing position in a four-batch program,
so there the pair (`-s0`, `-s0-again`) brackets the run instead of naming two
groups.

**The registers are one shared file, not one row per batch.** A store in a later
group still sees an earlier group's write: at size 2 `r2.lo` in batch 0 and
`r3.hi` in batch 1 read back together at the second group's store as
`0x7F000040` in both orders; the same pair reads the same word at every
group-start store at sizes 3 and 4, and every register half is visible from both
groups at size 3. Batch `i` does not own a private `r0..r3`. At size 1 the same
holds across every batch boundary, which is why the same-register test returns
`0x7F` for `0.25` then `0.5`, and `0x40` for the reversed order.

**At size N the DW runs once per group of N batches, from the first batch of the
group, at the end of it.** The ladder names the batch each store sees:

| size | store in batch 0 | 1 | 2 | 3 | 4 | 5 |
|--:|:--|:--|:--|:--|:--|:--|
| 1 | batch 0 | batch 1 | batch 2 | batch 3 | - | - |
| 2 | batch 1 | nothing | batch 3 | nothing | - | - |
| 3 | batch 2 | nothing | nothing | batch 5 | nothing | nothing |
| 4 | batch 3 | nothing | nothing | nothing | - | - |

Size 1 is the trivial case: every batch's DW fires at the end of its own batch
and sees its own write. Sizes 2, 3 and 4 are the rule exactly: only the group's
first batch stores, at the end of its group, so it sees the last write of its
group - including writes made in a *later* batch of the same group, which are
only later in program order because the DW runs at the group's end. Size 3 shows
two groups doing this independently, group 0's store naming batch 2 and group
1's naming batch 5.

The four-batch grid at size 2 is the same rule (`40` is the written `0.25`, `.`
is `0x00000000`):

| write in | store in 0 | 1 | 2 | 3 |
|:--|:--|:--|:--|:--|
| batch 0 | `40` | . | `40` | . |
| batch 1 | `40` | . | `40` | . |
| batch 2 | . | . | `40` | . |
| batch 3 | . | . | `40` | . |

At size 1 the grid is lower-triangular (a write is visible to its own batch's
store and every later one); at size 4 it is a single non-empty column, because
only batch 0 stores and it sees every write. At size 3 the grid is two
three-batch blocks: writes from batches 0, 1 and 2 appear in columns 0 and 3,
and writes from batches 3, 4 and 5 only in column 3, since the group-1 store
runs after them.

**A second DW in the group suppresses that group's store.** A store in every
batch zeroes sizes 2, 3 and 4, so the obvious reading was "the DW must be alone
in its group". `--mode arb` asks the smaller question: which combinations of two
DWs do that? One group per variant (`count = size`), every batch writing its own
byte, so the single-DW case names the group's last batch:

| DW placed in | size 2 | size 3 | size 4 |
|:--|:--|:--|:--|
| first batch only (`-a`) | `0x20` | `0x40` | `0x60` |
| second batch only (`-b`) | `0x00000000` | `0x00000000` | `0x00000000` |
| first and second (`-a-b`) | `0x00000000` | `0x00000000` | `0x00000000` |
| first and last (`-a-last`) | - | `0x00000000` | `0x00000000` |
| every batch (`-all`) | `0x00000000` | `0x00000000` | `0x00000000` |

So it is not "the DW must be the last operation" and not "the later DW wins": a
group with the first batch's DW *and* any second DW stores nothing at all. The
zero-returning control makes that more than an inference from a zero word -
`-a-b-zero` puts `store rt1, r0, r1` second, and `r0`/`r1` are never written, so
a second DW that stored would read `0x00000000` while `-a-b` (both storing the
written register) would still read the written byte. Both read zero, so neither
program produced an observable store - which of the two DWs, or the group's slot,
is responsible is not measured.

The effect is **per group**, not per program: `-local` puts two DWs in group 0
and the usual one in group 1 of a two-group program, and group 1 still stores
its own last batch (`0x60` at size 2, `0x9F` at size 3, `0xDF` at size 4). The
neighbouring groups are unaffected.

The `-b` row is why "a group with one DW stores" is not the rule: the lone DW
there is in the group's *second* batch, and it stores nothing. Every single-DW
control above puts its DW in the first batch, so the earlier statement was only
established for that position. `--mode dwpos` measures the others.

This is a rule about what is observed, not about why. Two DWs could be dropped
at decode, arbitrated away, or the group's store could be assigned an execution
slot that never comes; the template programs `pseq_to_dw_exec_nb = 1`, and a
program with more DWs than that field describes may simply not get a slot (the
pseq_to_dw_exec_nb sweep below tests that one and does not support it). Three
DWs in one group, a second DW in a group that also leaves an incomplete tail,
and the same experiment at a buffer size above 4 are untested, so the
statements here stay rules about arrangements rather than about a mechanism.

### Where in the group the one DW sits

A group's only DW was placed in its first batch in every control so far, and the
`-b` row shows the second batch failing at sizes 2, 3 and 4. `--mode dwpos` fills
in the positions the arb run leaves out - all four of a size-4 group and the one
cell still open at size 3 - with the same distinct write in every batch and the
template's `pseq_to_dw_exec_nb = 1`:

| buffer size | batch 0 | batch 1 | batch 2 | batch 3 |
|:--|:--|:--|:--|:--|
| 2 (`arb-n2-a`/`-b`) | `0x00000020` | `0x00000000` | - | - |
| 3 (`arb-n3-a`/`-b`, `dwpos-n3-b2`) | `0x00000040` | `0x00000000` | `0x00000000` | - |
| 4 (`dwpos-n4-b0`..`b3`) | `0x00000060` | `0x00000000` | `0x00000000` | `0x00000000` |

The position matrix is complete for sizes 2, 3 and 4, and it reads the same at
every size: the observable DW behaviour is **position-dependent inside the
group**, one DW stores when it sits in the group's first batch, and batches 1, 2
and 3 produce no observable store. The size-3 batch-2 case was run for coverage,
not because sizes 2 and 4 disagreed - they did not, and the size-4 variants
re-measured in that same run returned the four words above unchanged.

A store from batch 0 is not a store of batch 0's row: it returns `0x60`, the
group's last byte, rather than the byte of the batch its DW sits in, and
`dwpos-n4-b0` is the same program as `arb-n4-a` returning the same word from an
independent run.

"First batch" is relative to the group, not the program: the two-group runs put
a DW at the start of group 1 with no DW in group 0 (`xg-n4-wgroup1-store-g1`,
`0x40`) and it stores, and `arb-n4-local` still gets group 1's last byte while
group 0 carries two DWs.

This reads back into the two-DW result. `-a-b` differs from `-a` only by adding a
DW in batch 1, and a lone DW in batch 1 already stores nothing, so the pair's
zero is not by itself evidence of arbitration between two contending DWs: both
readings - a second DW cancels the group's store, or a DW outside the first batch
disables the slot - fit every run here. Recorded as measured over sizes 2 to 4,
the data say: an observable store comes from a group whose DW is in the group's
first batch and which has no other DW, and every other arrangement tested
produces nothing. Which of the two readings holds is not separated by these runs.

### At other `pseq_to_dw_exec_nb` values

The template programs `pseq_to_dw_exec_nb = 1`, so "more than one DW in a group
costs the group its store" could be a property of that configuration rather than
of the instructions: one reserved PSEQ-to-DW execution, two DWs asking for it.
The field is not a comment: in the source, `grate-asm.c` copies the header value
to `shader->pseq_to_dw_nb` and `grate_3d_set_pseq_dw_cfg()` programs it into
`FP_PSEQ_DW_CFG` (`0x546`) before the `0x520` start word, so rewriting the header
changes a register write rather than a comment. That path is read from the code,
not measured.

`--mode pseq` repeats the three discriminating sequences at 1, 2, 3, 4 and then
at 6, 8, 16 and 31, the last four inside the 6..31 range the blob's driver
writes: a limit that only showed at the field's normal settings would not appear
below them. The single-DW control stays in batch 0 at every value, which the
position sweep above shows is the one position where a lone DW stores at all.

| `pseq_to_dw_exec_nb` | `-a` (one DW, batch 0), n2 / n3 / n4 | `-a-b` | `-a-b-zero` |
|--:|:--|:--|:--|
| 1, 2, 3, 4 | `0x20` / `0x40` / `0x60` | `0x00000000` | `0x00000000` |
| 6, 8, 16, 31 | `0x20` / `0x40` / `0x60` | `0x00000000` | `0x00000000` |

Reserving up to 31 PSEQ-to-DW executions changes nothing. Every value stores the
group's last byte exactly once when the group has one DW in batch 0, and produces
nothing when it has two, and the zero-returning second DW again makes the two zero cases
indistinguishable: nothing becomes visible in either program.

Because the header is not the only path to the register, two variants at size 4
keep the header at 1 and write `0x546` directly in `GRATE_POKE_EARLY` (the poke
stage before the start word, when the sequencer latches it). `pseq1-n4-a-poke`
(`0x546 = 31 << 6`) still returns its `0x60`, so the program runs with the field
widened by a route that does not involve the header, and `pseq1-n4-a-b-poke`
still returns zero. The sweep above is therefore a register sweep and its zero is
not a header value that was parsed and dropped.

So a shortfall of reserved slots is not the explanation at any value of this
field, or the field does not gate that slot the way its name suggests. Which of
those holds is untested here, and so is whether the second DW is being dropped
before or after the field is consulted.

Only the eight values 1, 2, 3, 4, 6, 8, 16 and 31, sizes 2 to 4, and the three
sequences above are measured.
Size 1 is left out because a group is a single batch and so has no second batch
to hold a second DW; three DWs in one group remain untested at every value.

### Across a group boundary

The four-batch matrix gives most sizes a single group, so it cannot say whether
`r0..r3` survive a group boundary or are re-cleared at it. `--mode xgroup` runs
two whole groups (2 * size batches at `count = 2 * size`) with one write in group
0, nothing in group 1, and a store at each group's start:

| size | group 1 store, written in group 0 | same, nothing written | written in group 1 |
|--:|:--|:--|:--|
| 1 | `0x40` | `0x00000000` | `0x40` |
| 2 | `0x40` | `0x00000000` | `0x40` |
| 3 | `0x40` | `0x00000000` | `0x40` |
| 4 | `0x40` | `0x00000000` | `0x40` |

`0x40` is the written `0.25`. The write survives at every size, including size 4,
which the matrix could only see inside one group. The "nothing written" column
is the control that the group-1 store fired and read cleared state, so the
`0x40` is not a default. Writing a *different* constant in each group's first
batch (`-weach`) returns group 1's `0x7F`, so each group's store sees the newest
write rather than a rotated or per-group copy of the file.

### What the low field of `0x520` counts

Measured, not inferred, with a group ladder: eight batches, eight distinct
constants (`0x10 0x20 0x40 0x60 0x7F 0x9F 0xBF 0xDF`), and a store only in the
first batch of every group. Whichever store lands is the one from the last group
that ran, so the readback names the last batch executed. Thirty variants, one
poke each, 34 runs including repeats, from
`tests/grate/asm_characterize.alu_buffer_sweep.json` (34/34, which
`make_alu_buffer_matrix.py --mode sweep` regenerates):

| size | 1 | 2 | 3 | 4 | 6 | 8 | 9 | 10 | 11 | 12 | 14..32 |
|--:|:--|:--|:--|:--|:--|:--|:--|:--|:--|:--|:--|
| 1 | b0 | b1 | b2 | b3 | b5 | b7 | b7 | b7 | b7 | `0x10` | `0x10` |
| 2 | - | **b1** | - | b3 | b5 | b7 | - | - | - | none | none |
| 3 | - | - | b2 | - | b5 | - | b7 | - | - | none | none |
| 4 | - | - | - | b3 | - | b7 | - | - | - | none | none |

**One count is one batch, at every size.** At size 2 a count of 2 runs batches 0
and 1 and lands the store that batch 1 would have made in batch 0; if the field
counted execution slots, 2 would be a single two-batch group and the write would
name b0. It names b1. Size 3 (3 -> b2, 6 -> b5, 9 -> b7) and size 4 (4 -> b3,
8 -> b7) agree: `count = batches`, never `batches * size`.

Two edges, both measured:

* **past the program** the count stops tracking batches. At size 1, 9 and 10
  clamp at b7, 11 also returns `0xDF`, and 12 through 20 return `0x00000010` -
  the first constant, not a batch write, so the ladder has stopped meaning
  anything and something is re-fetching from the start. At sizes 2, 3 and 4 the
  same over-counts (12, 14, 16, 20, 24, 28, 32) land **nothing**:
  `0x00000000` every time.
* **well past the program** the channel wedges instead. Poking a count far above
  the batch count produced `tegra-mc ... EMEM address decode error` and then
  `****nvrm_init failed****` for every later run, which reads exactly like
  nondeterministic hardware and is not.

So the working count is the batch count; the slack is about two counts at size 1
and none worth using at sizes 2 to 4. Every manifest therefore runs its program
at the count equal to its length: 4 at sizes 1, 2 and 4, 6 at size 3.

**Reconciling this with `docs/hardware-testing.md` (reverse-engineering branch).**
That section reads the same field as execution slots and concludes the count must
be `batches * alu_buffer_size`. Both readings are of one field, and the
discriminator is small: a **two-batch** program at size 2 poked with count 2.
Under the slot reading, 2 is one batch's worth of slots, so the store in batch 0
fires and names `0x10`; the measured word names batch 1 (`0x20`), so a count of 2
is two batches. Every count in the old table that works is consistent with that:
6 on a three-batch program at size 2 is three complete groups, so the program
runs twice and the store still lands. Its hang rows (3, 5 and 7 at size 2) are
counts that leave an incomplete final group, not counts that are not multiples of
the size - the same hazard the size-4 row below documents. The old "batches
rotate over rows" table was measured with count 8 on a four-batch program, which
is two passes; at a matched count the grid shows one group's write visible to the
next group's store, so there is no rotation and there is one register file.

A count that hangs does not just fail itself: it wedges the channel and every
later variant in the same run times out. That is why the count probes
(`--mode count`) are ordered with the expected rejects last, and why a manifest
that needs an unknown count should be run on its own.

### Batch counts that leave an incomplete group

One edge is still not repeatable: a program whose batch count leaves an
incomplete final group. Three batches at size 4 returned `0x00000000` three times
in one session and hung three times in another, with no change to the template or
the poke; with the count read as batches, 12 also means the three-batch program
re-fetched four times, and which pass aligns a store with a group start depends
on the shape. Three batches at size 3 is a complete group and behaves normally.
The practical rule is unchanged: keep the batch count a multiple of the size,
which is what a scheduler would do anyway. The size-3 case that used to look
anomalous was this hazard plus an over-count, not a third DW.

The register reference notes that size 3 "runs *some* programs, hangs others";
this is a size-4 example of the same thing, and the honest rule for a shader
compiler is unchanged: keep the batch count a multiple of the size, which is what
a scheduler would do anyway.

**What this changes for a backend.** The old guidance ("the row file does not
carry from batch `i` to batch `i+1`") is wrong: the registers are one file and
values carry across batch boundaries at every size. What actually limits a wider
buffer is the DW: at size N only the first batch of each group can store, only
if the group has no other DW at all (a second one costs that group its store,
see the arbitration table), and the batch count has to be a multiple of N. A size-2 program can therefore hand values across the
boundary and store once per two batches, so it looks like it should halve the
store cost of the 13-batch `filter_quad` shape. **Measured: not resolved either way.** This
benchmark cannot separate one store per fragment from two (see "The size-2 store
win, measured" below), and `alu_buffer_size = 1` stays the default because every
store lands at its own batch and the count is the batch count.

**Traps, in the order they cost time.**

* **the poke has to be the whole start word.** `0x520` is `0x20006000 | count`,
  and poking the bare count replaces the start bits and hangs every size
  including 2. The same applies to the pokes quoted in
  `docs/hardware-testing.md`.
* **a store of an untouched row is `0x00000000`, so a zero is evidence - but
  only where the store runs.** Every group starts with the untouched-row control
  and ends with the same control again; both read zero, which is what lets
  "nothing visible" be a measurement rather than a missing one. A run that
  returns zero everywhere is only believable next to a variant that returns
  non-zero. The control has to be placed at a store position that fires: the
  first version kept its store at batch 1, which starts a group only at size 1,
  so at sizes 2 to 4 it ran no store at all and its zero proved nothing. Both
  controls now use the first and last entry of `store_positions()`.
* **check the poke the manifest actually carries before blaming the hardware.**
  See below: a whole run of sizes 3 and 4 returned zero because every variant
  was poked with the wrong count, and it looked exactly like a nondeterministic
  GPU.


### The size-2 store win, measured

The claim under test is that storing once per two-batch group halves the store
cost. The comparison has to be on a shape whose fragment program actually runs, so
`tests/grate/asm/store_cost_timing.sh` derives four variants of the shipped
`filter_quad_fs` (256x256 textured quad, two batches, one sample) and checks each
one with `--result` before timing it:

| variant | size | stores | notes |
|:--|--:|--:|:--|
| `base` | 1 | 1 | the shipped shader |
| `alu` | 1 | 1 | plus three ALU packets in batch 0: four times the ALU work |
| `st2` | 1 | **2** | a store in batch 0 as well |
| `n2` | 2 | **1** | `st2` at size 2, where only the group's first batch stores |

`st2` against `n2` is the win, if there is one: identical program text and store
layout, one parameter apart. `base` against `alu` is the sensitivity control.

`store_cost_timing.sh 6 400` - six rounds of 400 draws, with the config order
rotated by one per round, medians in ms:

| config | min | median | max | spread |
|:--|--:|--:|--:|--:|
| `base` | 557.2 | 585.6 | 608.3 | 51.1 |
| `alu` | 475.2 | 563.8 | 581.5 | 106.3 |
| `st2` | 468.8 | 528.8 | 633.0 | 164.2 |
| `n2` | 550.8 | 557.9 | 583.2 | 32.3 |

`st2` -> `n2` is **+29.0 ms, +5.5 %** - size 2 measures *slower*. The extra-store
delta (`st2` -> `base`) is -56.8 ms and the ALU control is -21.8 ms: more work
measuring faster, which is the signature of drift rather than of work. Every delta
is smaller than the spread of at least one config it comes from.

Earlier rounds of the same comparison, on the same shape but with a fixed config
order, are why this needed a rotation. At 100 draws and five rounds the medians
were 134.0 (`base`), 153.6 (`alu`), 156.8 (`st2`) and 147.7 (`n2`) ms, with `n2`
9.1 ms below `st2`; at 400 draws the same order gave 576.3, 578.9, 551.9 and
553.9, `n2` 2.0 ms below `st2`. A fixed order measures the last config warmest,
which is worth several ms and looks exactly like the predicted win. Rotating the
order turned the sign over.

**Verdict: not resolved by this benchmark.** The shape is one where the fragment
program is known to execute and the store layout differs by one store per
fragment, and the benchmark still cannot tell the two apart: size 2 measured 29 ms
slower with the order rotated and 2 to 9 ms faster with it fixed, while the
control that does four times the ALU work moved further than the difference under
test. Calling that "no win" would be over-reading the data; the honest statement
is that one store per fragment is smaller than this benchmark's drift. The size-2
side is also constrained structurally: at size 2 half the batches cannot store at
all, and the count cannot be raised to buy them back because it is the batch
count.

Two traps produced confident numbers that meant nothing before this shape was
established:

* **A draw that rasterises nothing times like a real one.** Hand-built eight-batch
  ALU shaders were first timed under `vs_mov` at 3.1 ms/draw in every shape,
  including one with four times the ALU work. Every one of those draws returned
  `0x4C4C4C4C`, the clear colour: the fragment program never ran and the whole
  comparison was submission overhead. `--result` must be checked before timing -
  `0x00000000` is the black texel a store wrote, `0x4C4C4C4C` is nothing at all -
  which is what `store_cost_timing.sh` does for all four variants and what makes
  the numbers above worth reading.
* **A failed run prints `-`, not a number.** A wedged channel gives no
  `elapsed_ms=` at all, and a summary script that assumes a float crashes on the
  first one (`could not convert string to float: '-'`) instead of reporting it.

## 4. MFU multiplier source select

The MFU word carries two 4-bit source numbers per multiplier. The mapping in
[[Fragment Shader ISA]] 6.3.2 came from probes that also carried interpolation
slots and several MFU words in one program; `fs_mfu_tests.txt` packs an SFU, two
multipliers and an interpolation into a single batch, so it cannot attribute a
result to one selector. This probe keeps exactly one MFU word per program.

Each variant is three batches at `alu_buffer_size = 1` from
`tests/grate/asm/mfu_sel.in`: batch 0 writes 0.0625, 0.125, 0.25 and 0.375 into
`r0..r3.low`, batch 1 holds the one word under test, batch 2 stores
`store rt1, r2, r3`. The store word is `r3.hi<<24 | r3.lo<<16 | r2.hi<<8 |
r2.lo`, so the multiplier's destination `r2` is the low 16 bits and the `0x60`
in byte 2 is `r3`'s primed 0.375, which doubles as a marker that the prime
arrived. Between variants only the source number changes.

| variant | word | reading |
|:--|--:|:--|
| `src-00`..`src-03` | `0x00600010`, `..0020`, `..0040`, `..0060` | row registers 0..3 |
| `src-04` | `0x00607F56` | internal, same value as the hand probe |
| `src-05`, `src-06` | `0x00600089`, `0x006000A9` | internal, same values |
| `src-07`, `src-08` | `0x00600000` | zero |
| `src-09` | `0x00600000` | zero without interpolation; the hand probe's `0x4100` had varyings active |
| `src-10` | `0x00600000` | the SFU result, with no SFU word in this program |
| `src-11`, `src-12` | `0x0060FF00` | identical with no varying fetch at all |
| `src-13` | `0x0060F700` | the `#1` constant |
| `src-14`, `src-15` | `0x00600000` | zero |
| `none` | `0x00600040` | control: no MFU word, the store returns the primed 0.25 |
| `noprime-src0` | `0x00000000` | control: no prime, so src0 reads nothing |

The two controls are what make the non-zero rows meaningful: `none` shows the
store and prime path work without any multiplier, and `noprime-src0` shows a
src0 product of zero when nothing was written, so a non-zero `src-00` cannot be
row state left over from somewhere else.

Read the `0x0010`..`0x0060` half as the bits the prime wrote, not as the number
the multiplier saw. The ALU writes `.l*` (fx10) and the multiplier reads the
same 16 bits as fp20, where `0x0010` is 2^-31; every product of two of these
primes in this section underflowed, which is the trap section 5 measures and
corrects.

Source 13 is the constant: `const13-times-src0` (`mul0: r2, src13, src0`)
returns `0x00600010`, the src0 value unchanged, so 13 multiplies as one and the
`#1` operand used in every other variant is a real 1.0. The product 1.0 x 1.0
itself (`src-13`) reads `0x0060F700`, i.e. `r2.lo` `0x00` and `r2.hi` `0xF7`,
not the saturated `0xFF` byte a 1.0 payload gives on the store path; recorded,
not explained.

**Two row-register operands read zero - superseded.** `mul0: r2, src2, src2`
(0.25 x 0.25), `mul0: r2, src3, src2` and `mul0: r2, src3, src3` all return
`0x00600000`, with the destination on one of the operands. Moving the
destination off both operands - `mul0: r3, src0, src1` and
`mul0: r3, src2, src3` - leaves r3 at `0x00` where it was primed at 0.375, so
the multiplier ran and wrote zero rather than not running.

That reading was wrong, and the reason is the prime format. These rows were
primed with `.l*` (fx10), and the multiplier reads a row as fp20: the same
16-bit word `0x0010` is 0.0625 as fx10 and 2^-31 as fp20. Two primes near the
floor of the format multiply to about 2^-60, which underflows to zero, so the
zero said nothing about the source fields. Primed `.lh` instead, the same
products are correct - section 5 has the 4 x 4 table. The `#1` case only looked
healthy in the same run because 1.0 x anything keeps the operand's own
encoding. Every zero in this section came from that, and the two-field
symmetry measurement above is unaffected: it compares a row against `#1`, i.e.
values that no underflow touches.

### Where the destination writes

`--set dst` (18 variants), same program, only the destination number changes.
Rows 4..7 multiply a row register whose value differs from the destination's
prime, so a write shows as a changed byte; each is also read through the store
pair it does *not* name, which must return its no-MFU baseline.

| variant | word | reading |
|:--|--:|:--|
| `none-store01` | `0x00200010` | baseline: r0.lo 0x10, r1.lo 0x20 |
| `none-store23` | `0x00600040` | baseline: r2.lo 0x40, r3.lo 0x60 |
| `dst4-store01` | `0x00200060` | `dst4` wrote r0 (0x60 = 0.375), r1 untouched |
| `dst5-store01` | `0x00600010` | `dst5` wrote r1, r0 untouched |
| `dst6-store23` | `0x00600010` | `dst6` wrote r2 (0x10 = 0.0625), r3 untouched |
| `dst7-store23` | `0x00100040` | `dst7` wrote r3, r2 untouched |
| `dst4-store23`, `dst5-store23` | `0x00600040` | the r2/r3 pair is the baseline, so only r0/r1 moved |
| `dst6-store01`, `dst7-store01` | `0x00200010` | the r0/r1 pair is the baseline, so only r2/r3 moved |
| `dst0..dst3-store01/store23` | `0x00200010`, `0x00600040` | both pairs are the baselines for all four numbers |

So destination 4..7 is a plain row-register index that writes exactly one
register, and 0..3 write none of the four row registers. The 0..3 variants use
1.0 as both operands, whose product carries `0xF7` in the `.hi` byte (see
`src-13`), so a write into a row register could not hide behind a prime.

### The second source field

`--set field` (8 variants). The source sweep only ever put the number under test
in the first field, and `src0` is the only row register the second field had been
shown with.

| variant | word | | variant | word |
|:--|--:|:--|:--|--:|
| `src13-x-src0` | `0x00600010` | | `src0-x-src13` | `0x00600010` |
| `src13-x-src1` | `0x00600020` | | `src1-x-src13` | `0x00600020` |
| `src13-x-src2` | `0x00600040` | | `src2-x-src13` | `0x00600040` |
| `src13-x-src3` | `0x00600060` | | `src3-x-src13` | `0x00600060` |

Each order returns the same word, so both fields select row registers and 13
multiplies as 1.0 in either slot. That is what rules out the obvious explanation
of the two-row-register zeros - the second field cannot be the field that
refuses, because it selects a row register correctly when the other operand is
1.0.

### Source 10 and the SFU result

`--set sfu` (8 variants). One MFU word holds an sfu sub-instruction and both
multipliers, so `sfu: rcp r3 mul0: r2, src10, #1` is a single word.

| variant | word | reading |
|:--|--:|:--|
| `nosfu-src10` | `0x00600000` | comparison: the same multiply with no sfu sub-instruction |
| `sfu-rcp3-src10` | `0xFF00FF00` | r3 = 0xFF00 is the SFU's write, r2 = 0xFF00 the multiply |
| `sfu-rcp1-src10` | `0x0060FF00` | SFU wrote r1 instead, r3 keeps its 0x60 prime, src10 still 0xFF00 |
| `sfu-rcp3-src0` | `0xFF000010` | the sfu sub-instruction does not disturb a multiply of r0 |
| `sfu-rcp3-only` | `0xFF000040` | the SFU alone wrote r3 = 0xFF00, both bytes changed |
| `sfu-rcp1-only` | `0xFF000010` | the SFU alone wrote r1 = 0xFF00, r0 untouched |
| `sfu-sqrt3-src10` | `0x7BFF7BFF` | sqrt into r3, and src10 returns the same value |
| `sfu-sqrt0-src10` | `0x00607BFF` | sqrt naming r0 gives the same 0x7BFF, r3 keeps its prime |

So source 10 exposes the SFU result of the same MFU word, and it is SFU state
rather than a row register: moving the SFU's output to r1 leaves r3 primed while
src10 still returns 0xFF00.

### What the SFU reads

The `--set sfu` words above cannot say what the unit reads, because every one of
them primed the rows with `.l*`, and that writes only the low fx10 half of a row.
Section 12.7 of [[Fragment Shader ISA]] reads an fp20 destination back through
the byte above that half, so an fx10 prime leaves the fp20 field zero and the
unit computes on the floor of the format: sqrt(2^-31) is 2^-15.5, whose readback
byte is `0x7B`, and rcp(2^-31) is 2^31, which saturates to `0xFF`. That is the
whole of `0x7BFF` and `0xFF00` - they are not the root and reciprocal of the
primed 0.375.

`--set fp20` (6 variants) writes the rows with `.lh`, which stores a real fp20
value, so the op finally has a result to check against section 12.7's table.

| variant | word | reading |
|:--|--:|:--|
| `fp20-none-store23` | `0xEB00E700` | no MFU word: the fp20 primes, r2 0.25 -> `E7`, r3 0.375 -> `EB` |
| `fp20-sqrt3-only` | `0xF000E700` | sqrt of r3 (0.375) -> `F0`; r2 untouched |
| `fp20-sqrt3-src10` | `0xF000F000` | src10 returns the same fp20 the SFU wrote to r3 |
| `fp20-sqrt2-src10` | `0xEB00EF00` | sqrt of r2 (0.25) = 0.5 -> `EF`; r3 keeps `EB` |
| `fp20-sqrt0-src10` | `0xEB00E700` | sqrt of r0 (0.0625) = 0.25 -> `E7` |
| `fp20-rcp3-src10` | `0xFF00FF00` | rcp of 0.375 = 2.67, above 2.0, so it saturates |

Three named registers give three different results, each the root of the value
primed there, so the register in `sfu: op rN` is the operand - in place, as
`docs/assembler-syntax.md` says (`sfu: RCP r1` means r1 = 1.0 / r1) - and the
earlier "the named register is the destination, not the input" reading is
withdrawn. `fp20-sqrt3-only` shows that same register receiving the result.
`0xF0` for sqrt(0.375) is the readback of 0.5625: 0.6124 with its mantissa
truncated to the three bits the byte carries, which is the byte that predictor
gives, while the unrounded value would land a step higher.

The `0xF700` of the 1.0 x 1.0 product is settled by the same table: fp20 1.0
reads back as `F7 00`, so it is exactly 1.0 rather than an unexplained value.

### Row 4 and the clip w

`--set w` (12 variants) points the SFU at r4, the register docs section 6.5
gives the fragment's w, and moves only the vertex shader: `vs_scale_w.txt`
multiplies clip x, y, z and w by one uniform, so x/w, y/w and z/w do not change
and the quad covers the same pixels.

| variant | w | word | reading |
|:--|--:|--:|:--|
| `w1-sqrt4`, `w0.25-sqrt4`, `w4-sqrt4` | 1, 0.25, 4 | `0x0060FF00` | sqrt >= 2.0 at every w |
| `w1-rcp4` | 1 | `0x00607800` | rcp ~ 1/2^16 |
| `w0.25-rcp4` | 0.25 | `0x00606800` | two octaves lower, so the operand is four times larger |
| `w4-rcp4` | 4 | `0x00608700` | two octaves higher, four times smaller |
| `w1-lg2-4`, `w4-lg2-4` | 1, 4 | `0x0060FF00` | lg2 >= 2.0, so the operand is at least 4 |
| `w1-rsq-4` | 1 | `0x0060B700` | rsq = 1/256, so the operand is 2^16 |
| `w4-rsq-4` | 4 | `0x0060BF00` | rsq = 1/128, so the operand is 2^14 = 2^16/4 |
| `w0.25-nosfu`, `w4-nosfu` | 0.25, 4 | `0x00600000` | baseline: no SFU word, so nothing reaches the store |

So r4 follows the fragment's w, and what the unit reads there is the reciprocal
as a plain number: about 2^16 / w. rcp moves two octaves for a fourfold w, rsq
lands on 1/256 and 1/128, and sqrt and lg2 both saturate - a 0..1 operand would
make sqrt(1/4) = 0.5 (`EF`) and lg2(1/4) = -2 (`E7`) at w = 4, and both read
`FF` instead. The readback resolves eight steps per octave, so the constant is
consistent with 2^16 to within one step; the register supplies 1/w on a
16.16-style fixed scale rather than as a fraction, which is why the unit's
result is scaled too (rcp of it is w/2^16). The no-SFU baselines are identical
at both w, so the store word did not move with the geometry, and the scale-1.0
anchors reproduce the earlier unscaled words.

A trap to record: the first attempt at this run named r3 instead of r4 and
returned one word for all three w. Naming a row the pipeline does not fill
cannot test what the pipeline fills, and the flat result looked like "the SFU
ignores w" until the operand itself was checked.

### Selectors 11 and 12 against real interpolation

The source sweep read `0xFF00` for both selectors, which is the readback of a
value at or above 2.0 - not a 0..1 weight - and it did so without fetching a
varying, so it could not say what they are. `--set bary` (43 variants) reads them
with the vertex shader translating the quad, because the harness reads pixel
(0, 0) of `tools/assembler.c`'s fixed quad. Both readings are taken at several
positions, and the last four groups also export data back through the same
`ipl` so the sample point itself can be measured.

| variant | word | reading |
|:--|--:|:--|
| `p0-none` | `0x00600040` | no MFU word: the primed rows |
| `p0-raw`, `p1-raw` | `0xFF00FF00` | both selectors at or above 2.0 on their own |
| `p2-raw` | `0xFF40FF00` | still saturated; the low byte is the readback's residue |
| `p0-scale`, `p1-scale`, `p2-scale` | `0x78007800` | `1.0 x rcp(r4)`, the scale reference |
| `p0-coef` | `0xAF00F600` | src11 `F6`, src12 `AF` |
| `p1-coef` | `0xE300F200` | src11 `F2`, src12 `E3` |
| `p2-coef` | `0xDC40F400` | src11 `F4`, src12 `DC` |
| `p1-coef-noipl` | `0xE300F200` | identical with no fetch in the word |
| `p1-swap-coef`, `p2-swap-coef` | `0xF200E300`, `0xF400DC40` | the fields mirror, so the value follows the selector, not the multiplier |
| `p1-interp-rg`, `p1-interp-ba` | `0xD300F200`, `0xF700E300` | a full `ipl` with `bar` weights, storing the interpolated varying |
| `constvar-rg`, `constvar-ba` | `0xE700EF00`, `0xF700F300` | a *constant* varying `(0.25, 0.5, 0.75, 1.0)` reads back as `(0.5, 0.25, 0.75, 1.0)` |
| `p1-pos-rg`, `p1-pos-ba` | `0xE740E300`, `0xF7000000` | the sample's quad-space position, exported as the varying |
| `p3-pos-rg`, `p3-interp-rg`, `p3-coef` | `0xDC40E800`, `0xE300F2AB`, `0xF2ABE300` | the sample moved across the quad's diagonal |
| `p4-pos-rg`, `p4-coef` | `0xEEFFEEFF`, `0xEEFFEFFF` | the sample at the quad centre |
| `p4-interp-rg`, `p4-interp-ba` | `0x0000EFFF`, `0xF700EEFF` | the interpolated colour there |
| `constvar2-rg`, `constvar2-ba` | `0xE700EF00`, `0xF7000000` | the same constant exported as two components reads identically |
| `s1a-*`, `s1b-*` | see below | single-triangle samples, triangle (0,1,2) collapsed |
| `wwa-*`, `wwb-*` | see below | the same, with unequal clip w per vertex |

The readback is a log byte, so the difference to the `0x78` scale reference
divided by 8 is log2 of the coefficient, and the scale in r4 cancels:

| sample point in the quad | src11 | src12 |
|:--|--:|--:|
| corner pixel, offset `(0, 0)` | 0.84..0.92 | 0.0016..0.0018 |
| `(-0.50, -0.65)`, offset `(-0.5, -0.4)` | 0.60..0.65 | 0.165..0.18 |
| offset `(-0.25, -0.2)` only, position not exported | 0.71..0.77 | 0.088..0.096 |
| `(-0.08, -0.08)`, the quad centre | 0.50..0.54 | 0.459..0.50 |

So both selectors are per-pixel weights: they move with the sample position, and
they are delivered with the fragment rather than fetched - dropping the `ipl`
leaves them byte-identical. On their own they read as saturated because they
carry a 2^16 scale; multiplying by `rcp(r4)`, which is w/2^16, cancels it and
gives the coefficient itself. That is the arithmetic of section 6.4's
`weight = coef * 1.0 / w` at w = 1, measured with the same word that measures
`rcp(r4)`. The two multipliers must also be shown not to be the thing that
decides: with `src12` and `src11` exchanged the two fields exchange with them
(`0xF200E300` against `0xE300F200`), so the numbers follow the selector.

The zero-offset sample sits on the corner pixel, not on the vertex: the quad's
lowest vertex is at the pixel's corner and the rasteriser covers the pixel with
an interior fragment, so its coefficients are 0.84..0.92 and 0.0016..0.0018
rather than 1 and 0. Read it as a near-corner sample, not as an exact vertex.

#### The sample point, and what the weights are

Three things had to be measured before the selectors could be named.

The *store order* is not the varying's component order. Exporting a constant
`(0.25, 0.5, 0.75, 1.0)` and fetching it back gives `(0.5, 0.25, 0.75, 1.0)`
(`constvar-rg`): with `store rt1, r0, r1` the low half of the result word
carries the varying's `y` and the high half its `x`, while `z` and `w` keep
their order. A two-component export of the same constant reads identically
(`constvar2-rg`), so the exchange is not the export's component mask. It cannot
be pinned to the store by writing the halves the other way round either - the ISA
only encodes the pairs `r0,r1` and `r2,r3`, so `store rt1, r1, r0` does not
assemble. Every two-component readback below is decoded with the exchange
applied, and the uneven-w probe at the end is the one place where that matters
for more than bookkeeping.

The *vertex colours are the unit vectors* `(1,0,0)`, `(0,1,0)`, `(0,0,1)`,
`(1,0,0)` on v0..v3 (`tools/assembler.c`), drawn as triangles (0, 1, 2) and
(1, 2, 3). In a triangle whose vertices are v1, v2, v3 the interpolated colour is
therefore `(w3, w1, w2)` - red is v3's weight, green v1's, blue v2's - so on
`w = 1` geometry the colour readback gives all three weights directly, with no
geometry to model. In triangle (0, 1, 2) it is `(w0, w1, w2)`.

The *single-triangle probe* removes the shared diagonal. The vertex shader moves
the blue vertex (v2) onto v0 with `x += -2 * a[1].z`, which collapses triangle
(0, 1, 2) onto a line, so every sample is interior to (1, 2, 3). Its attribute
stays at the original corner, so the interpolated position is a weighted sum of
the original corners rather than the sample's own coordinate - the colour is the
reliable readback there, not the position.

With that, the selectors have a name. In triangle (1, 2, 3):

| variant | colour `(R,G,B)` under the exchange | selectors | reading |
|:--|:--|:--|:--|
| `p1-coef`, `p1-interp-*` | 0.044, 0.648, 0.177 | 0.648, 0.177 | src11 = green = w1, src12 = blue = w2 |
| `p4-*` (centre) | 0, 0.50, 0.46 | 0.50, 0.46 | src11 = w1, src12 = w2 |
| `s1a-*` | 0.42, 0.46, 0.05 | 0.46, 0.05 | src11 = w1, src12 = w2 |
| `s1b-*` | 0.42, 0.18, 0.33 | 0.18, 0.33 | src11 = w1, src12 = w2 |

and in triangle (0, 1, 2):

| variant | colour `(R,G,B)` | selectors | reading |
|:--|:--|:--|:--|
| `p3-coef`, `p3-interp-rg` | 0.177, 0.648, - | 0.177, 0.648 | src11 = red = w0, src12 = green = w1 |

So `src11` is the barycentric weight of the covering triangle's first vertex and
`src12` that of its second, in the index order the harness draws. Both triangles
agree with that rule, and the (1, 2, 3) rule is measured at four separate sample
points, including two where the sample is the only triangle's interior.

This is also where the earlier reading went wrong: with the exchange ignored, the
p3 colour looks like it belongs to the other triangle, and the weights appear to
swap between samples. Nothing in the hardware needed to change for the rule to
hold - only the decode.

#### Normalization

Because the colour channels are the weights, all three are now measured
independently rather than two and a remainder: at p1 0.044 + 0.648 + 0.177 =
0.869, at the centre 0 + 0.50 + 0.46 = 0.96, at `s1a` 0.42 + 0.46 + 0.05 = 0.93,
at `s1b` 0.42 + 0.18 + 0.33 = 0.93. Every sum is short of 1 by 4-13%, and each
channel is truncated to three mantissa bits, so the deficit is the same size as
the readback's own step. The sum is consistent with exact normalization but does
not prove it: a uniform scale applied to all three would look identical.

#### Unequal w

The last group sets clip w from the colour attribute (`w = 1 + a[1].z`, so the
blue vertex has w = 2 and the others w = 1), which projects the quad into a
trapezium and turns on perspective-correct interpolation:

| variant | word | reading |
|:--|--:|:--|
| `wwa-coef` | `0xE100F4FF` | src11 0.77, src12 0.15 |
| `wwa-interp-rg`, `wwa-interp-ba` | `0x0000F4FF`, `0xF700E100` | colour 0 / 0.77 / 0.15 |
| `wwb-coef` | `0xF000E700` | src11 0.25, src12 0.55 |
| `wwb-interp-rg`, `wwb-interp-ba` | `0xE700F000`, `0xF700DF00` | colour 0.55 / 0.25 / 0.12 |

At `wwa` the selectors and the colour agree; at `wwb` they do not. This probe
turns w on, but it also moves the projected triangle - the shader sets clip w
without premultiplying x, y and z, so the vertices divide by a different w and
the trapezium is not the quad the `w = 1` samples were taken on. The two samples
therefore cannot be compared point by point, and the disagreement says nothing
yet about which quantity carries the 1/w. The `persp` set below holds the
projection fixed and answers it.

#### Perspective correction with the projection held fixed

The `persp` set (38 variants) premultiplies the clip position by a per-vertex w,
so `x/w` and `y/w` - everything the rasteriser sees - are identical for every w
and only the interpolation weights move. w is 1 at every vertex except the blue
one, which carries `1 + wdelta` for wdelta in 0, 1, 3, i.e. w = 1, 2 and 4. The
sample points sit inside triangle (1, 2, 3), where lambda = `(1-x)/2`,
`(1+y)/2`, `1 - lambda_1 - lambda_2`:

| point | sample | lambda | w = 4: `D` |
|:--|:--|:--|:--|
| `q1` | (0.75, 0.45) | 0.125, 0.725, 0.15 | 0.456 |
| `q2` | (0.35, -0.35) | 0.325, 0.325, 0.35 | 0.756 |
| `q3` | (-0.6, -0.8) | 0.8, 0.1, 0.1 | 0.925 |

`D` is the perspective denominator `sum lambda_i / W_i`. Each point is read at
each w three ways: the coefficient (`src11`/`src12` times `rcp(r4)`), a scalar
varying, and `src13 x rcp(r4)` as an anchor for `r4` itself. A `-pos` variant
reads the sample point back with the same program (both triangles drawn, the
position exported as the varying), which is how the three rows above are
confirmed: the words put the samples at (0.756, 0.354), (0.242, -0.379) and
(-0.631, -0.799), each within one readback step of the intended point.

**The ratio of the two selectors scales with w, exactly.** This needs no model
of the geometry at all - both selectors are read from the same word, so their
ratio is free of the readback's absolute scale:

| point | w = 1 | w = 2 | w = 4 | ratio to the w = 1 row |
|:--|:--|:--|:--|:--|
| `q2` | 1.000 | 2.000 | 4.000 | x2.00, x4.00 |
| `q3` | 7.33 | 16.0 | 29.3 | x2.18, x4.00 |
| `q1` | 0.180 | 0.324 | 0.707 | x1.80, x3.93 |

So `src11 / src12 = (lambda_1 / W_1) / (lambda_2 / W_2)`: the second selector is
divided by its vertex's w and the first is divided by 1. A screen-space pair
would keep the ratio constant across w, and these move by 2 and 4.

**The anchor moves with `D`.** `src13 x rcp(r4)` reads `1/(65536 D)`:

| point | w | reading | `1/(65536 D)` |
|:--|:--|:--|:--|
| `q2` | 2 | 1.81e-5 | 1.81e-5 |
| `q2` | 4 | 1.99e-5 | 1.99e-5 |
| `q1` | 4 | 3.05e-5 | 3.10e-5 |
| `q3` | 2, 4 | 1.66e-5, 1.66e-5 | 1.61e-5, 1.65e-5 |

`q3` is the case where `D` moves by less than one readback step, so its word not
moving is consistent rather than evidence. Reading the two rows together, `r4`
carries the fragment's interpolated `1/w` - the same `D` the coefficient path
divides by - which is what section 6.4 of the docs calls the `1.0 / w` the
coefficient is multiplied with.

**The coefficient is the perspective weight.** With `coef = selector x rcp(r4)`
the second selector's coefficient separates the candidates, since a screen-space
selector would give `lambda_2 / D`, which is above 1 for w = 2 and 4 and would
read saturated:

| point | w | measured | `(lambda_2/W_2)/D` | `lambda_2/D` |
|:--|:--|:--|:--|:--|
| `q1` | 2 | 0.545 - 0.595 | 0.569 | 1.137 |
| `q1` | 4 | 0.354 - 0.386 | 0.397 | 1.589 |
| `q2` | 2 | 0.177 - 0.193 | 0.194 | 0.388 |
| `q2` | 4 | 0.096 - 0.105 | 0.107 | 0.430 |
| `q3` | 4 | 0.026 - 0.029 | 0.027 | 0.108 |

Every row is within one readback step of the perspective value and 2 to 4 steps
from the screen-space one. The first selector's coefficient has both models
agree (its vertex has w = 1) and is within a step of `lambda_1 / D` throughout.

**The interpolated varying is perspective-corrected too**, which is what makes
the above the same quantity the varying path uses rather than a coincidence:

| sample | w | measured | perspective | screen space |
|:--|:--|:--|:--|:--|
| `q1` | 4 | 0.545 - 0.595 | 0.565 | 0.394 |
| `q2` | 4 | 0.648 - 0.707 | 0.705 | 0.594 |
| `q2` asymmetric | 4 | 0.771 - 0.841 | 0.825 | 0.639 |

The vertex values are `(1.0 at v3, 0.5 at v1, 0.25 at v2)` for the first two
rows and `(0.375, 1.5, 0.0625)` for the third, set through uniforms. The
asymmetric set exists to remove the vertex-colour channel order from the decode:
the varying is one scalar made from the three colour channels and then
replicated across all four components, so neither the store's x/y exchange nor
the channel-to-vertex mapping enters these numbers.

What this does not settle: every value here is a one-step bracket (three mantissa
bits, 12.5% wide in value) and the predictions sit inside them, so the probe
cannot separate exact normalization from a common factor on all weights - the
same caveat as the equal-w sums. `q3` is in the set as the control where the two
models differ by less than a step.

### What is left

The other SFU operations can now be driven with known inputs (`.lh` primes) and
characterised one at a time, and the two-row-register zero is resolved: it was
an fx10 prime read as fp20 (section 5). What that leaves on the multiplier is
identity, not behaviour - which internal state selectors 4, 5, 6 and 9 read, and
whether destination 0 names a fourth weight the hardware does not use. The
readback's three mantissa bits bound everything here to one step, which is why an
exact normalization constant is still not measured. The constant in r4 is
resolved to the same one step; the `persp` set pins its *relative* behaviour
against `D` instead, so a probe that reads the operand at a coarser magnitude
would only be needed for the absolute value.

## 5. MFU multiplier source/destination matrix

`--set matrix` (112 variants) from `tests/grate/asm/mfu_matrix.in`, manifest
`asm_characterize.mfu_selector_matrix.json`. The four sets above each varied one
field of one multiplication; this one runs the table - every pair of row
registers with the destination on neither operand and then on each of them, both
multipliers alone and together, both source fields for every number that has no
row register behind it, and destinations 0..3 in the word that interpolates.

The template is `mfu_sel.in` plus one thing: the prime batch carries an MFU word
of its own (`@MFU0@`). The stage order inside a batch is MFU, TEX, ALU, DW, so
that word runs *before* the ALU primes and the batch-1 word after them, which is
what lets a variant write a piece of fragment state one batch before the word
that reads it.

### The prime format, not the source field, produced the zeros

The multiplier reads a row register as fp20. `.l*` writes fx10, and the same 16
bits are not the same number in the two formats: `0x0010` is 0.0625 as fx10 and
2^-31 as fp20. So `src-00`..`src-03` above show that the row's *bits* come
through a multiply by 1.0, not that 0.0625 did, and every product of two such
primes in the earlier sets was a product of two values at the floor of the
format.

With the same programs primed `.lh` the whole 4 x 4 table multiplies. Each cell
is the fp20 byte the destination holds after `mul0: dst, srcI, srcJ`; the primes
are r0 = 0.0625 (`0xD7`), r1 = 0.125 (`0xDF`), r2 = 0.25 (`0xE7`), r3 = 0.375
(`0xEB`):

| first / second | r0 | r1 | r2 | r3 |
|:--|:--|:--|:--|:--|
| **r0** 0.0625 | `0xB7` | `0xBF` | `0xC7` | `0xCB` |
| **r1** 0.125 | `0xBF` | `0xC7` | `0xCF` | `0xD3` |
| **r2** 0.25 | `0xC7` | `0xCF` | `0xD7` | `0xDB` |
| **r3** 0.375 | `0xCB` | `0xD3` | `0xDB` | `0xE0` |

Every cell is the product to within the readback's three mantissa bits (one
step is 12.5% in value): 0.0625 x 0.125 = 0.0078 = 2^-7 lands exactly on
`0xBF`, 0.25 x 0.375 = 0.0938 reads `0xDB` (0.088) and 0.375 x 0.375 = 0.1406
reads `0xE0` (0.136). The 16 words, in that reading order:

| variants | words |
|:--|:--|
| `fp20-rows-0x0`..`0x3` | `0xB700D700`, `0xEB00BF00`, `0xC700D700`, `0xCB00D700` |
| `fp20-rows-1x0`..`1x3` | `0xEB00BF00`, `0xDF00C700`, `0xDF00CF00`, `0xDF00D300` |
| `fp20-rows-2x0`..`2x3` | `0xC700D700`, `0xDF00CF00`, `0xDF00D700`, `0xDF00DB00` |
| `fp20-rows-3x0`..`3x3` | `0xCB00D700`, `0xDF00D300`, `0xDF00DB00`, `0xDF00E000` |

Both halves are readable because the destination is never on an operand:
whichever register of the store pair receives the result, the other one keeps
its prime (`0xD7`, `0xDF`, `0xE7`, `0xEB`), so every word above carries a prime
in one half and a product in the other.

The `fx10-` twins of those 16 - the same programs primed `.l*`, exactly as the
earlier sets were - return `0x0000` in the destination half in all 16 cases. The
primes are 2^-31 there and the product of two of them is 2^-62, below the floor
of the format. So the zeros are underflow, not a rejected source combination,
and "two row-register sources read zero" is withdrawn.

**The destination's position does not matter.** Eight variants repeat four of
these products with the destination moved onto the first and onto the second
operand - the arrangement every earlier zero was measured in - and all eight
return the product: `0xDF00BF00`, `0xBF00D700`, `0xCF00D700`, `0xEB00CF00`,
`0xEB00DB00`, `0xDB00E700`, `0xDF00CB00`, `0xCB00E700`.

### Every source class multiplies every other

What the sweep never crossed: a row against the SFU result, a row against a
coefficient, the SFU result against itself, and a coefficient against the other
coefficient. All with fp20 primes, so nothing underflows:

| variant | word | reading |
|:--|--:|:--|
| `class-sfu-x-row0` | `0xF000D000` | sqrt(0.375) = `0xF0` (0.612) x 0.0625 = 0.038, read as `0xD0` (0.034) |
| `fp20-row0-x-sfu` | `0xF000D000` | the same product with the fields exchanged |
| `class-sfu-x-sfu` | `0xF000EB00` | 0.612 x 0.612 = 0.375, `0xEB` |
| `fp20-const-x-sfu` | `0xF000F000` | 1.0 x 0.612 |
| `class-row0-x-bar0` | `0xEB00FF00` | 0.0625 x a coefficient: saturated, since a coefficient is >= 2.0 unscaled |
| `class-bar0-x-row0` | `0xEB00FF00` | the same |
| `class-bar0-x-bar1` | `0xEB00FF00` | two coefficients, saturated |
| `class-13-x-bar0` | `0xEB00FF00` | 1.0 x a coefficient, saturated |
| `class-sfu-x-bar0` | `0xEB00F600` | rcp(r4) x coefficient = 0.917, the coefficient at the corner pixel |

So no pair of source classes reads zero on its own account; the only zeros in
this set are the fx10 twins of the row table. The `class-sfu-x-bar0` reading is
the interesting one for the interpolation: it is the same product as the
established `mul0: ..., src11, sfu` with the operands exchanged, at the corner
pixel where section 4 measured 0.84-0.92.

### The two multipliers

| variant | word | reading |
|:--|--:|:--|
| `mul1-row0` | `0xEB00D700` | `mul1` writes the register it names (r2 = 0.0625), from a row source |
| `mul1-13-x-row0` | `0xEB00D700` | and with 13 in the first field |
| `mul1-rows0-x-1` | `0xEB00BF00` | and two row registers multiply: 0.0625 x 0.125 = `0xBF` |
| `mul1-dst6` | `0xEB00D700` | `mul1`'s destination field maps like `mul0`'s: 6 writes r2 |
| `both-independent` | `0xE700DF00` | r0 = 0.125 from `mul0`, r1 = 0.25 from `mul1`, one word |
| `both-same-dest-01` | `0xDF00E700` | both write r0: `mul0`'s 0.25 survives, `mul1`'s 0.375 does not |
| `both-same-dest-23` | `0xEB00D700` | both write r2: `mul0`'s 0.0625 survives |
| `both-rows` | `0xDB00E700` | `mul0` 0.25 in r0, `mul1`'s row product 0.0938 in r1 |

So the two units are independent - separate source and destination numbering,
two products in one word - and when both name the same register the first
multiplier's value is the one left behind. That is a measurement, not a rule
about what a compiler may emit.

### The numbers with no row register behind them

Selectors 4..9 and 14..15, each in the first field against `#1`, in the second
field against 13, and at a pixel inside the triangle instead of on the corner
(the source sweep's sample). Values are the stored register after the multiply
by 1.0:

| selector | first field | second field | inside | with a fetch |
|:--|:--|:--|:--|:--|
| 4 | `0x7F56` | `0x7F56` | `0x7F56` | `0x7F56` |
| 5 | `0x0089` | `0x0089` | `0x0089` | `0x0089` |
| 6 | `0x00A9` | `0x00A9` | `0x00A9` | `0x00A9` |
| 7 | `0x0000` | `0x0000` | `0x0000` | - |
| 8 | `0x0000` | `0x0000` | `0x0000` | - |
| 9 | `0x0000` | `0x0000` | `0x0000` | `0x4100` |
| 14, 15 | `0x0000` | `0x0000` | `0x0000` | - |

Neither the field nor the pixel position moves them, so 4, 5 and 6 read state
that is neither per-pixel nor field-specific, and 7, 8, 14 and 15 read nothing
at all. Selector 9 is the exception: it is zero in every program without a

(`sel9-ipl-fx10`), so what it reads is tied to the fetch happening rather than

### Destinations 0..3 are the interpolated weight

The blob writes both multipliers to `bar`, i.e. destination 1, in the same word
as the fetch, and none of 0..3 writes a row register, so the interpolation is
the only place they can show. Substitute each one for `bar` in that word and
compare the interpolated colour. At the sample point `p1` the control is
`0xD300F200`, which decodes - the store puts the varying's `y` in the low half
and `x` in the high half - to the colour (0.044, 0.65) that section 4 attributes
to that pixel:

| variant | word | reading |
|:--|--:|:--|
| `weight-bar` | `0xD300F200` | control: `mul0: bar, sfu, bar0` |
| `weight-dst1` | `0xD300F200` | destination 1 instead of `bar`: identical |
| `weight-dst2` | `0xD300F200` | destination 2: identical |
| `weight-dst3` | `0xD300F200` | destination 3: identical |
| `weight-bar-q2` | `0xCB00F400` | control at a second sample point |
| `weight-dst1-q2`..`dst3-q2` | `0xCB00F400` | all three identical again |

So 1, 2 and 3 all supply the weight the interpolator uses - at two sample points
with different weights, which is what rules out three distinct weights that
happen to agree - and 0 supplies nothing: with `mul0` writing destination 0 the
fetch returns `0xF300AF00` at the first point and `0xF5FFAF00` then `0xF5FFAF40`
at the second, the last differing in its low byte between two runs of the same
program. Undefined state is not pinnable, which is why those two variants are
not in the manifest.

**A weight written a batch earlier - see section 6.** `keep-dst0`..`keep-dst3`
write 1.0 into one of the four destinations in the prime batch and then run the
control's fetch word; all of them, and `keep-none`, return the control's
`0xD300F200` byte for byte. That says only that the fetch word's own write
wins, since it recomputes both weights, so the pair below removes that write
from the fetch word instead. In `keep-w0-none` the multiplying word writes only
w1, and in `keep-w0-one` w0 = 1.0 was written one batch earlier:

| variant | prime batch | fetch word | word |
|:--|:--|:--|--:|
| `keep-none` | nothing | `mul0: bar`, `mul1: bar` | `0xD300F200` |
| `keep-dst1` | `mul0: dst1, 1.0` | `mul0: bar`, `mul1: bar` | `0xD300F200` |
| `keep-w0-none` | nothing | `mul1: bar` only | `0xF300AF00` |
| `keep-w0-one` | `mul0: dst1, 1.0` | `mul1: bar` only | `0xF300AF00` |

The last two agreeing was read here as "the earlier weight is not carried into
the interpolator, so both multipliers have to be in the word that fetches". That
reading does not hold: `keep-w0-none` leaves w0 to whatever the fetch finds, and
an unwritten weight does not give a defined word. Section 6 runs the same pair
at two MFU slots and gets `0xF300AF00` and `0xBD00AF00`, and with a control that
writes both weights the earlier write is read (`w0-one-prev` and `w0-one-same`
both `0x0000F701`). The two rows stay as measured; the conclusion drawn from
them, and the scheduling restriction it implied, are withdrawn.

## 6. Where a weight has to be written

The matrix set closed by saying that a weight written in an earlier batch is not
used by a later fetch. That was wrong, and the comparison it rested on had no
defined weight on either side: `keep-w0-one` and `keep-w0-none` both wrote only
`w1` and left `w0` to whatever the fetch found, and an unwritten weight is not
zero. Both returned `0xF300AF00` in that manifest, which was read as "the
earlier write changed nothing"; in the set below the same incomplete pair reads
`0xF300AF00` at one MFU slot and `0xBD00AF00` at the next.

This set (`--set chain`) gives batch 1 three MFU sub-instructions, so the
weights and the fetch can be moved between words without touching PSEQ, TEX, ALU
or DW. Every variant here writes both weights, so every word is a defined
interpolation.

| variant | weights written in | fetch in | word |
|:--|:--|:--|:--|
| `same-word` | batch 1 word 1 | word 1 | `0xD300F200` |
| `next-word` | batch 1 word 1 | word 2 | `0xD300F200` |
| `next-word-nosfu` | batch 1 word 1 | word 2, no sfu | `0xD300F200` |
| `two-words-before` | batch 1 word 1 | word 3 | `0xD300F200` |
| `fetch-before-weight` | batch 1 word 2 | word 1 | `0xF600B800` |
| `one-one-same` | batch 1: both 1.0 | word 1 | `0x0001F701` |
| `one-one-prev` | batch 0: both 1.0 | word 1 | `0x0001F701` |
| `w0-one-same` | batch 1: `w0` = 1.0, `w1` from `mul1` | word 1 | `0x0000F701` |
| `w0-one-prev` | batch 0: `w0` = 1.0 | word 1 | `0x0000F701` |
| `none-weights` | - | word 1 | `0xB400BB00` |
| `garbage-first` | `w1` only | word 1 | `0xF300AF00` |
| `garbage-second` | `w1` only | word 2 | `0xBD00AF00` |

**The fetch does not have to be in the weight's word, or in the next one.** Both
weights written two MFU words before the fetch interpolate exactly as the
same-word control does, and the word between them can be a multiply. What the
batch does require is order: with the fetch in the first word and the weights in
the second, the fetch reads something else (`0xF600B800`), so it uses what the
batch has written *before* it and not what comes after.

**A weight written a batch earlier is used.** `one-one-same` writes both weights
as 1.0 in the fetch word and `one-one-prev` writes the same pair in batch 0:
both return `0x0001F701`. `w0-one-same` (w0 = 1.0 and w1 from the multiplier,
both in the fetch word) and `w0-one-prev` (w0 one batch earlier) both return
`0x0000F701`, and `rcp-twice` - the blob's weight word in *both* batches - still
returns the same-word `0xD300F200`. The same pair of programs in the matrix
template's one-slot shape (`one-slot-same`, `one-slot-prev`) returns
`0x0000F701` as well, so this is not the batch length; the matrix manifest's
`0xF300AF00` was the unfinished pair, not a dropped write.

**An unwritten weight is neither zero nor stable.** `garbage-first` and
`garbage-second` hold the same `w1`-only words in different MFU slots and read
`0xF300AF00` and `0xBD00AF00`; `none-weights`, which writes nothing, reads
`0xB400BB00`. That is why every variant in this set writes both weights, why the
matrix set's `keep-*` pair cannot be used as evidence, and why destination 0 is
described rather than pinned in either set.

**Destinations 1, 2 and 3 supply the weight from either unit.** With `mul0` as
the producer and `mul1` writing its own weight to `bar`, `mul0-dst1`,
`mul0-dst2` and `mul0-dst3` all return the `both` control's `0xD300F200`; with
`mul1` as the producer, `mul1-dst1`, `mul1-dst2` and `mul1-dst3` return it too.
That is the matrix paragraph's observation, now for both units. It does not show
that the three numbers name one register: the hardware derives the third weight
as `1 - w0 - w1` and hardwires `mul0` to `w0` and `mul1` to `w1` (the blob's
semantics, 6.4 of the ISA document), so "the weight" and "w0" as destination
names would look the same from outside. Destination 0 writes no weight either
way.

Runs: 22 variants, 70 rows including the two controls before and after, three
repeats each; `pin-mfu-chain` and `verify-mfu-chain` are 70/70 each, the pin is
idempotent, and pin and verify agree word for word.

## 7. The SFU opcode matrix

`--set ops` (121 variants) from `tests/grate/asm/sfu_ops.in`, manifest
`asm_characterize.sfu_ops.json`. Every decoded special-function opcode is run at
representative inputs: RCP, RSQ, LG2, EX2, SQRT, SIN, COS, FRC, PREEX2, PRESIN
and PRECOS. The PRE ops are run both alone and with their main op, because
EX2/SIN/COS are documented as second steps. Each variant is five batches at
`alu_buffer_size` 1:

    batch 0   prime r0=0.75, r1=0.5, r2=1.0, r3=input
    batch 1   up to three MFU words
    batch 2   up to three MFU words
    batch 3   ALU readout
    batch 4   store r2, r3

so the PRE and main words can be in the same batch or one batch apart, and only
the fields being measured change between variants. Every variant writes all
four row registers before reading one.

### Reading the result without decoding fp20

The raw 16-bit result in the named register is not converted by the store path:
DW's reading of an fp20 field is logarithmic at the byte level, and the low byte
is not a simple mantissa. Every row here therefore takes the result through the
multiplier's `sfu` source in the same MFU word and converts it to fx10 in the
ALU:

    sfu: rcp r3  mul0: r2, sfu, #1  mul1: r3, sfu, r1

with r1 = 0.5, so r2 holds the value and r3 half of it. The ALU writes both as
`.l*`, which DW reads as a linear 0..1 byte. The half copy keeps 1.414
distinguishable from 2.0, but anything at or above 2.0 still reads `0xFF`; the
amplified variants below cover those cases. The `none` control has no SFU word
and returns `0xEF7FF7FF`: r2 = 1.0 reads `0xFF`, r3 = 0.5 reads `0x7F`. In every
word quoted, the low byte of each 16-bit half is the converted value.

For an exactness measurement the r2 conversion is replaced with
`K*(value-expected)+0.5` at K = 256. `0x7F` is the expected value; one count is
1/(255*256) = 1.5e-5, and one fp20 ulp at 0.5 is 2^-14 = 6.1e-5, so about four
counts. The expected value is computed from the fp20 the assembler actually
stores - its `float_to_fp20` truncates the mantissa - not from the decimal
input, so `sin(pi/6)` is checked at 0.5234375.

### Every opcode writes the register it names

`inplace-*` runs the op with no multiplier and stores r2 and r3. r2 stays its
1.0 prime in all eleven variants, and r3 changes from the input prime to:

| op | input | r3 word after | op | input | r3 word after |
|:--|--:|--:|:--|--:|--:|
| `rcp` | 1.5 | `F100` | `cos` (after `precos`) | 0 | `F700` |
| `rsq` | 4.0 | `EF00` | `frc` | 1.75 | `F300` |
| `lg2` | 1.5 | `F0FF` | `preex2` | 1.0 | `FF00` |
| `ex2` (after `preex2`) | -1.0 | `EF00` | `presin` | 1.0 | `FF5F` |
| `sqrt` | 0.25 | `EF00` | `precos` | 1.0 | `FF5F` |
| `sin` (after `presin`) | pi/6 | `EE00` | | | |

The input prime for `cos` is `0000` and for `frc` `F300`, so each row is a
different word from what the register started with. The named register is the
operand and the destination, as `docs/assembler-syntax.md` says; the result is
also available to the multipliers of the same word (`none` and the `sfu`
source variants above).

### What each opcode returns

The pair variants run the PRE word first and the main word second, both naming
r3. The value is the readout byte, quantised to 1/255, with the r3 half used when
the value is between 1 and 2. Quoted words are r2|r3.

**RCP and RSQ.** RCP is the reciprocal and RSQ the reciprocal square root over
the positive range; the readout is the exact decimal rounded to the nearest 1/255
where that is possible, so `1/1.5` reads 170 (`0.667`) and `1/2` reads 127
(`0.498`):

| `rcp` input | value | word | `rsq` input | value | word |
|--:|--:|:--|--:|--:|:--|
| 0.5 | 2.0 | `F7FFFFFF` | 0.0625 | 4.0 (amplified) | `FFFFFF7F` |
| 0.75 | 1.333 | `F1AAF9FF` | 0.25 | 2.0 (amplified) | `F7FFFF7F` |
| 1.0 | 1.0 | `EF7FF7FF` | 0.5 | 1.412 | `F2B4FAFF` |
| 1.5 | 0.667 | `E955F1AA` | 1.0 | 1.0 | `EF7FF7FF` |
| 2.0 | 0.5 | `E740EF7F` | 2.0 | 0.706 | `EA5BF2B4` |
| 4.0 | 0.25 | `DF20E740` | 4.0 | 0.5 | `E740EF7F` |
| -1.0 | -1.0 (amplified) | `0000007F` | -1.0 | maximum | `FFFFFFFF` |
| 0.0 | maximum | `FFFFFFFF` | 0.0 | maximum | `FFFFFFFF` |

The negative RCP result is measured by the amplified variant, not by the raw
word: the plain readout clamps everything below zero to `0x00`, so `rcp(-1)`
reads `0x00000000` there. RSQ of a negative input returns the same maximum as
RSQ of zero, which is what `RCP(SQRT(x))` predicts (`sqrt(-1)` is 0 below), but
this set does not establish that as the mechanism.

**LG2 and FRC.** LG2 returns log2, including negative results; the plain readout
clamps them, and the amplified rows at 0.5 and 0.25 show -1 and -2. FRC is
floor-based: the two negative inputs give positive fractions.

| `lg2` input | value | `frc` input | value |
|--:|--:|--:|--:|
| 0.25 | -2.0 (amplified) | 0.25 | 0.25 |

| 1.0 | 0 | 1.0 | 0 |
| 1.25 | 0.322 | 1.25 | 0.25 |
| 1.5 | 0.584 | 1.5 | 0.5 |
| 2.0 | 1.0 | 1.75 | 0.75 |
| 3.0 | 1.584 | 2.0 | 0 |
| 4.0 | at least 2.0, reads the ceiling | -0.25 | 0.75 |
| | | -1.25 | 0.75 |

`lg2(4)` reads `F7FFFFFF`: r2 saturates and r3 is 2.0, which is also the
ceiling, so this row proves `>= 2` rather than exactly 2. The fractional rows
are the same values as `frc(x)` for x and x+1, and `frc(-1.25) = 0.75`
distinguishes floor from truncation (truncation would read 0).

**SQRT and EX2.** SQRT is the square root; SQRT of a negative input is exactly
0 (the amplified row against 0.0 reads `0x7F`, so it is not a negative result
clamped by the readout). EX2 is `2^x` only when its PRE step is present.

| `sqrt` input | value | word | `ex2` input (with `preex2`) | value | word |
|--:|--:|:--|--:|--:|:--|
| 0.0625 | 0.25 | `DF20E740` | -2.0 | 0.25 | `DF20E740` |
| 0.25 | 0.5 | `E740EF7F` | -1.0 | 0.5 | `E740EF7F` |
| 0.375 | 0.612 | `E84EF09C` | -0.5 | 0.706 | `EA5BF2B4` |
| 0.5 | 0.706 | `EA5BF2B4` | 0.0 | 1.0 | `EF7FF7FF` |
| 1.0 | 1.0 | `EF7FF7FF` | 0.25 | 1.184 | `F097F8FF` |
| 1.5 | 1.224 | `F09CF8FF` | 0.5 | 1.412 | `F2B4FAFF` |
| 2.0 | 1.412 | `F2B4FAFF` | 1.0 | at least 2.0 | `F7FFFFFF` |
| 4.0 | at least 2.0 | `F7FFFFFF` | 2.0 | at least 2.0 | `FFFFFFFF` |
| -1.0 | exactly 0 | `00000000` | | | |

**SIN and COS.** Both are second steps and need PRESIN/PRECOS. The input is in
radians: `sin(1) = 0.839` and `cos(1) = 0.537` are the radian values, not the
turn-based ones. The rows at 2*pi and pi return the function's values there;
this set does not test arguments beyond 2*pi, so it says nothing about how far
the reduction extends.

| `sin` input | value | word | `cos` input | value | word |
|--:|--:|:--|--:|--:|:--|
| 0.0 | 0 | `00000000` | 0.0 | 1.0 | `EF7FF7FF` |
| pi/6 | 0.498 | `E640EE7F` | pi/6 | 0.867 | `EC6FF4DD` |

The negative sine and cosine rows are below zero and clamp in the plain

### The second steps without their first step

Three controls run EX2, SIN and COS alone in one MFU word, with no PRE word:

| variant | word | read value | pair reads |
|:--|--:|--:|--:|
| `ex2-alone-m1` | `0xEF7FF7FF` | 1.0 | 0.5 |
| `sin-alone-p1` | `0xEF7FF7FF` | 1.0 | 0.839 |
| `cos-alone-p0` | `0x00000000` | 0.0 | 1.0 |

So EX2 at -1.0 without PREEX2 reads 1.0 (`2^0`), SIN at 1.0 without PRESIN
reads 1.0, the operand rather than `sin(1)`, and COS at 0 without PRECOS reads
0. None of the three is usable alone. The earlier survey saw the same shape
over more inputs; this run has one control row for each and a pair at the same
input to compare against.

### What the first step leaves

The PRE ops alone, read through the same `sfu` source in their own word:

| op | input | read value | word |
|:--|--:|--:|--:|
| `preex2` | -1.0 | 0.5 | `E740EF7F` |
| `preex2` | 0.0 | 0 | `00000000` |
| `preex2` | 0.5 | 1.498 | `F3BFFBFF` |
| `preex2` | 1.0 | at least 2.0 | `F7FFFFFF` |
| `presin` | 0.0 | 0 | `00000000` |
| `presin` | pi/6 | at least 2.0 | `FFFFFFFF` |
| `presin` | 1.0 | at least 2.0 | `FFFFFFFF` |
| `presin` | pi | at least 2.0 | `FFFFFFFF` |
| `precos` | 0.0 | 1.0 | `EF7FF7FF` |
| `precos` | 1.0 | at least 2.0 | `FFFFFFFF` |
| `precos` | pi | 0 | `00000000` |

These are intermediates, not the main function: `preex2(0)` is 0 rather than 1,
`preex2(0.5)` is 1.498 rather than 1.414, and `presin(pi/6)` is already at or
above 2. The values are what the `sfu` source returns in the PRE's own word;
they are not a coherent function of the input and are not used by the main step
as a normal operand. The set records them so that a later pairing probe has a
baseline; it makes no claim about the internal representation beyond the six
rows.

### Multiplier interaction and ordering

The SFU is evaluated before the multipliers of its word, and the multipliers
can read the result:

| variant | word | reading |
|:--|--:|:--|
| `order-rcp` | `0xF700F100` | r3 = 1.0 (mul0 wrote it), r2 = rcp of the *old* 1.5 (`F100`) |
| `order-sqrt` | `0xF700EF00` | r3 = 1.0, r2 = sqrt of the old 0.25 (`EF00`) |
| `both-rcp` | `0xEF00EF00` | rcp(2.0) = 0.5 reaches both r2 and r3 |

So neither multiplier's destination clobbering the operand changes what the
SFU read, and both multipliers see the same `sfu` result in one word. The
amplified rows also take their value through `mul0: r2, sfu, #1` and still read
`0x7F`, so the multiplier does not lose a visible fraction of the result at this
resolution.

### Observed precision

Twenty-three amplified function rows, each with a known expected value, at 256
times the error plus 0.5 (the separate `preex2` row is the sampled PRE
intermediate, not a function result):

| ops and inputs | byte |
|:--|--:|
| `rcp` 0.25 (4.0), 1.5, 3.0; `rsq` 0.0625 (4.0), 4.0, 0.25 (2.0); `lg2` 0.5 (-1.0), 0.25 (-2.0); `ex2` -1.0, 0.5; `sqrt` 0.25, 2.0, 4.0, -1.0 (0.0); `cos` 0; `frc` -0.25, 1.75 | `0x7F` |
| `lg2` 1.5 | `0x7C` |
| `sin` pi/6 | `0x7C` |
| `sin` -pi/6 | `0x83` |
| `cos` 2*pi/3 | `0x7C` |

`0x7F` is the exact value; three counts are 4.6e-5 and four are 6.1e-5, so the
four non-exact rows are within one fp20 ulp at 0.5. The `sin` and `cos` rows
are also within the input truncation: the assembler stores
`pi/6` as 0.5234375, whose sine is 0.4998605, not 0.5. This is the same
accuracy the earlier amplified probes found for the first-step ops, and it
extends it to the PRE pairs and to negative results. It does not separate the
unit's own rounding from the one-ulp input truncation.

### What this set does not settle

* The 16-bit fp20 word is not decoded here. The evidence is the linear readout
  after the multiplier; the raw words in the `inplace-*` rows are recorded but
  not interpreted, and the low byte is visibly not part of the same scale as the
  high byte.
* The PRE first step's output is only sampled, not modelled. The pairing set is
  the place to establish which operations invalidate a pending intermediate and
  how far apart the two words may be.
* SIN/COS are sampled to 2*pi and at -pi/6 only; arguments beyond 2*pi and the
  exact argument-reduction range are not covered.
* `lg2(4)` is only bounded below by 2.0 because both readout scales saturate
  there; the `lg2(2) = 1.0` row is exact.
* SFU opcodes outside 0..11, and the `unknown` MFU word fields, are not touched.

## 8. The PRE step and its main op

`--set pair` (50 variants) from `tests/grate/asm/sfu_pair.in`, manifest
`asm_characterize.sfu_pair.json`. The template primes the rows, then carries six
batches of three MFU words (W0..W17), so the first and second words of a pair
can sit one to seventeen words apart and cross up to five batch boundaries.
Batch 1 also has an ALU stage after its MFU words, which is where the ALU
clobber writes the operand between the two words. The last two batches convert
r2 and r3 to fx10 and store them.

The base pair is `PRESIN r3` of 1.0 followed by `SIN r3` with
`mul0: r2, sfu, #1`. The readout is the same linear byte as section 7: the
working pair reads `0xD6` (0.839), and `SIN` without its first step returns the
operand 1.0 and reads `0xFF`. `PAIR-ex2` of -1.0 reads `0x7F` (0.5) and its
alone control `0xFF` (1.0); `PAIR-cos` of 0 reads `0xFF` (1.0) and its alone
control `0x00` (0). A destroyed pair is therefore a different byte from the
control in every family, not a matter of decoding a value.

### Separation

The main word is placed at W1, W2, W3, W4, W5, W6, W9, W12, W15 or W17; W3 is
already the next batch, and W17 is five batch boundaries away:

| main at | word |
|:--|--:|
| W1, W2, W3, W4, W5, W6, W9, W12, W15, W17 | `0xF4D6F4D6` |

Every one returns the pair result, so the tested working separation is
**17 MFU words and five batch boundaries**. `gap-ex2-12` (`0xEF7FEF7F`) and
`gap-cos-17` (`0xF7FFF7FF`) repeat the same result for the other two main ops,
so the survival is not specific to SIN. This is a lower bound: nothing here
says the limit is 17.

### The main has to name the PRE's register

| variant | word | reading |
|:--|--:|:--|
| `reg-pre0-main0` | `0xEF7FF4D6` | both name r0: r2 = 0.839, pair works |
| `reg-pre0-main3` | `0xF7FFF7FF` | main names r3 instead: r2 = 1.0, no result |
| `reg-pre3-main1` | `0xEF7FF3BF` | main names r1: r1 stays its 0.5 prime (the `7F` half); r0's converted prime is `BF` |
| `reg-pre3-main1-then3` | `0xF4D6F4D6` | the r1 word is a no-op; the later r3 main still works |

So the register field selects the pending intermediate as well as the operand:
a main word naming another register writes nothing there and does not disturb
the pair. This is the same "no write" the `presin-r3-sin-r2` row in the SFU
matrix showed.

### A write to the operand destroys the pair

The pair is `PRESIN r3` at W0 and the main at W3; W1 or the batch-1 ALU writes
between them:

| variant | write between the words | word | main returns |
|:--|:--|--:|--:|
| `clobber-none` | none | `0xF4D6F4D6` | 0.839 |
| `clobber-mul-same` | `mul0: r3, src13, src13` (the same 1.0) | `0xF7FFF7FF` | 1.0, the operand |
| `clobber-mul-different` | `mul0: r3, r0, src13` (0.75) | `0xF3BFF3BF` | 0.75, the operand |
| `clobber-alu-same` | ALU `MAD r3.lh, u8, #1, #0` (1.0) | `0xF7FFF7FF` | 1.0 |
| `clobber-alu-different` | ALU `MAD r3.lh, u7, #1, #0` (0.75) | `0xF3BFF3BF` | 0.75 |
| `clobber-mul-other` | `mul0: r1, src13, src13` | `0xF4D6F4D6` | 0.839 |
| `clobber-alu-other` | ALU write to r1 | `0xF4D6F4D6` | 0.839 |

Both the multiplier and the ALU can destroy the pair, and writing the same
value back is no better than writing a different one. A write to another
register is harmless. The main then behaves exactly like its alone control
(0.839 pair vs 1.0 or 0.75 operand), so this class of clobber clears the
intermediate rather than poisoning it.

### Which SFU operations disturb a pending pair

An SFU word on r3 sits at W1 between the PRE and the main at W3. `-cap` uses a
multiplier to capture the intervening result, so the op cannot be skipped as an
uncaptured second step:

| intervening op | word | pair result |
|:--|--:|:--|
| `cos` | `0xF4D6F4D6` | survives |
| `cos` with a capture | `0xF4D6F4D6` | survives |
| `sin` | `0xF4D6F4D6` | survives |
| `sin` with a capture | `0xF4D6F4D6` | survives |
| `rcp` | `0x00000000` | 0 |
| `rsq` | `0x78007800` | 0 |
| `lg2` | `0xCD07CD07` | 0.027 |
| `ex2` | `0xF3C3F3C3` | 0.765 |
| `sqrt` | `0xF6F4F6F4` | 0.957 |
| `frc` | `0x00000000` | 0 |
| `preex2` | `0x00000000` | 0 |
| `presin` | `0x00000000` | 0 |
| `precos` | `0xF7FFF7FF` | 1.0 |

Nine of the eleven change the pair, but not to the alone-control value: RCP or
SQRT of 1.0 is still 1.0, yet the following SIN returns 0 or 0.957 rather than
the 1.0 it would return with no PRE at all. So these ops poison the pending
intermediate instead of clearing it, and the resulting value is not a function
of the new operand alone. SIN is harmless because the main does not consume the
intermediate (below); COS is harmless even when its own result is captured, so
with a PRESIN pending it appears not to execute at all. That last point is
observed, not explained.

The repeat-PRE rows are the same shape: a second `PRESIN` of the same 1.0 while
the first is still pending gives 0 as an intervening op, and re-arming after a
main gives `0xF2BEF2BE` (0.745) rather than the 0.839 of a fresh pair. So a
repeated PRE on the same register does not simply replace the old intermediate.
A PRE on a *different* register does not disturb the pair: placing `PREEX2 r1`
between `PRESIN r0` and its main returns both results correctly (below).

### The main does not consume the intermediate

| variant | words | word | reading |
|:--|:--|--:|:--|
| `main-twice` | PRESIN, SIN, SIN | `0xF4D6F4D6` | second SIN also reads 0.839 |
| `main-thrice` | PRESIN, SIN, SIN, SIN | `0xF4D6F4D6` | third SIN too |
| `rearm` | PRESIN, SIN, PRESIN, SIN | `0xF2BEF2BE` | a second PRE corrupts the result |
| `rearm-other` | PRESIN r3, SIN, PREEX2 r0, SIN r3 | `0xF4D6F4D6` | a PRE elsewhere is harmless |

So the intermediate outlives its own main and can drive the same main again;
what it does not survive is another PRE on the same register. A compiler can
therefore reuse a pending pair, but must not re-emit the first step for the
same operand while it is still live.

### Two chains in flight

The operands are in r0 and r1 and the two results go to r2 and r3, so one word
shows both:

| variant | words | word | reading |
|:--|:--|--:|:--|
| `interleave-sin-ex2` | PRESIN r0, PREEX2 r1, SIN r0, EX2 r1 | `0xEF7FF4D6` | r2 = 0.839 (sin), r3 = 0.5 (ex2) |
| `interleave-ex2-sin` | PREEX2 r1, PRESIN r0, EX2 r1, SIN r0 | `0xF4D6EF7F` | r2 = 0.5, r3 = 0.839 |

with both results in one word and a capture for each.

### What this set does not settle

* Why COS with a PRESIN pending is harmless; the set only observes that it
  leaves the pair word unchanged, with and without a capture multiplier.
* What the poisoned values from RCP/SQRT/LG2/... mean. They are recorded as
  words, not decoded; the point is only that they are neither the correct pair
  result nor the alone-control value.
* Whether the 17-word separation is a limit or just the largest tested. There
  is no failing case here.
* TEX writes and multi-slot (four-ALU) writes between the two words, and more
  than two interleaved chains, are not covered.
* The ALU clobber is applied in the same batch as the PRE, after the MFU stage;
  an ALU write in a later batch between the words is not tested.

## 9. Scalar-slot forwarding inside an ALU packet

`--set fwd` (55 variants) from `tests/grate/asm/alu_fwd.in`, manifest
`asm_characterize.alu_fwd.json`. Three batches at `alu_buffer_size` 1:

    batch 0   prime r2 = 0.25 in both fx10 halves, r3 = 0.75
    batch 1   the producer and consumer slots
    batch 2   store r2, r3

The producer writes 0.5 to `r2.l*`; the consumer copies `r2.l` to `r3.l*`. A
stored word is `r3 << 16 | r2`, so the low byte of the high half is the
consumer's linear value: `0x7F` means it saw 0.5, `0x40` means it read the 0.25
prime. r2 is primed in both halves and r3 in its low half before any read, and
the same consumer in batch 2 is the register-file control.

### The row register does not forward, in either slot order

| producer slot → consumer slot | word |
|:--|--:|
| p0→c1, p0→c2, p0→c3, p1→c2, p1→c3, p2→c3 | `0x0040407F` |
| p1→c0, p2→c0, p2→c1, p3→c0, p3→c1, p3→c2 | `0x0040407F` |

All twelve return the same word: `r2.lo = 0x7F` shows the producer's write did
land in the register by the end of the packet, and `r3.lo = 0x40` says the
consumer read the 0.25 prime. A consumer after the producer does not see the
produced value any more than a consumer before it. Moving the same consumer one
batch later gives `0x007F407F` (`r3.lo = 0x7F`), so the difference is the packet
boundary, not the instruction pair.

A plain reading of the ISA note that "each instruction in a package can use
partial results from the previous instruction" therefore does not hold for a
row register destination. The partial-result path that does work is the recv
accumulator below.

### Producers and consumers across opcodes

Producer in slot 0, consumer in slot 1. `MUL` is the addition-disable form, so
it writes two products; `MIN`/`MAX` compare the two products `rA*rB` and
`rC*rD`, which is why their operands are chosen to make both products 0.5
rather than 0.

| variant | producer | consumer | word |
|:--|:--|:--|--:|
| `op-prod-mad` | `MAD r2.l*, u4, #1, #0` | `MAD r3.l*, r2.l, #1, #0` | `0x0040407F` |
| `op-prod-mul` | `MUL r2.l*, u4, #1, u4` | same | `0x00407F7F` |
| `op-prod-mul-diff` | `MUL r2.l*, u4, #1, u2` | same | `0x0040407F` |
| `op-prod-min` | `MIN r2.l*, u4, #1, u4` | same | `0x0040407F` |
| `op-prod-max` | `MAX r2.l*, u4, #1, u2` | same | `0x0040407F` |
| `op-cons-mad` | `MAD r2.l*, u4, #1, #0` | `MAD r3.l*, r2.l, #1, #0` | `0x0040407F` |
| `op-cons-mul` | same | `MUL r3.l*, r2.l, #1, #1` | `0xFF40407F` |
| `op-cons-min` | same | `MIN r3.l*, r2.l, #1, #1` | `0x0040407F` |
| `op-cons-max` | same | `MAX r3.l*, r2.l, #1, #0` | `0x0040407F` |

In every row the producer's value (0.5, or 0.5 in both halves for `MUL`) is in
r2 by the end (`r2.lo = 0x7F`; high byte `0x40` where the other half was not
written), and every consumer returns `r3.lo = 0x40` - the prime. `op-cons-mul`
also writes its second product (1.0, `0xFF`) to r3's other half. Neither the
producer nor the consumer opcode changes the result.

### Destination masks and source formats

| variant | producer | consumer reads | word |
|:--|:--|:--|--:|
| `part-lo-read-hi` | `MAD r2.l*, u4` (0.5 low) | `r2.h` | `0x0040407F` |
| `part-hi-read-lo` | `MAD r2.*h, u4` (0.5 high) | `r2.l` | `0x00407F40` |
| `part-hi-read-hi` | `MAD r2.*h, u4` (0.5 high) | `r2.h` | `0x00407F40` |
| `part-lh-read-fp20` | `MAD r2.lh, u4` (fp20 0.5 = `0xEF00`) | `r2` (fp20) | `0x0040EF00` |
| `part-lh-read-h` | same | `r2.h` | `0x0000EF00` |

A one-half write leaves the other half at its prime (`0x40`), and a consumer
reading the written half still gets the prime, not the producer's 0.5, in both
the fx10 and fp20 source formats. `part-lh-read-h` reads the fp20 word's high
byte (`0xEF`), which as an fx10 half is `0x00` - `.lh` does not write a usable
fx10 half.

### The recv accumulator is the partial-result path

`(this)` is the recv bit and `(other)` the send bit. A consumer with `(this)`
has rC overridden by the previous slot's result and added in. Word layout again
`r3 << 16 | r2`; the `r2.lo` column is the producer's own write.

| variant | instruction pair | word | r2.lo | r3.lo |
|:--|:--|--:|--:|--:|
| `acc-none` | 0.25; 0.5, no modifiers | `0x0040407F` | 0.5 | 0.25 |
| `acc-this-01` | 0.25 `(this)`; 0.5 `(this)` | `0x00BF4040` | 0.25 | 0.75 |
| `acc-this-12` | same in slots 1 and 2 | `0x00BF4040` | 0.25 | 0.75 |
| `acc-this-012` | 0.125, 0.25, 0.5 all `(this)` | `0x00BF4060` | 0.375 | 0.75 |
| `acc-this-only-0` | 0.25 `(this)`; 0.5 plain | `0x00404040` | 0.25 | 0.25 |
| `acc-this-only-1` | 0.25 plain; 0.5 `(this)` | `0x00FF407F` | 0.5 | 1.0 |
| `acc-other-01` | 0.25 `(other)`; 0.5 `(this)` | `0x00BF4040` | 0.25 | 0.75 |
| `acc-both-01` | 0.25 `(this)(other)`; 0.5 `(this)` | `0x00BF4040` | 0.25 | 0.75 |
| `acc-send-12` | 0.25 `(other)` in slot 1; 0.5 `(this)` in slot 2 | `0x00BF4040` | 0.25 | 0.75 |
| `acc-xpacket` | 0.25 `(this)` batch 1; 0.5 `(this)` batch 2 | `0x007F4040` | 0.25 | 0.5 |
| `acc-xpacket3` | 0.25 `(this)` in batch 1 slot 3; 0.5 `(this)` batch 2 slot 0 | `0x007F4040` | 0.25 | 0.5 |

What the words show:

* a consumer with `(this)` returns 0.5 + the **previous slot's raw result**:
  0.75 from 0.5 and 0.25. The producer does not need `(this)` for that -
  `acc-this-only-1` returns 1.0 from a plain 0.5 writer;
* the forwarded value is the previous slot's own result, not its accumulated
  one: in `acc-this-012` the middle slot writes 0.375 (0.25 + 0.125) to r2, but
  the third slot adds 0.25 and returns 0.75;
* `(this)` on a producer with no predecessor adds nothing (0.25 + 0 = 0.25);
* `(other)`/send changed nothing in these three layouts - all still return the
  0.75 that `(this)` alone gives;
* the accumulation does not cross a packet boundary in either test. Batch 2's
  ALU0 recv returns 0.5, not 0.75, even when batch 1's ALU3 was the 0.25
  producer.

### Several slots writing one half OR their results

The four-packet result-register set turned this up: two slots writing `r2.lo`
with 0.25 and 0.5 left 0.75, not 0.5. The fwd template has one packet with one
constant per slot:

| variant | values written to r2.lo | word |
|:--|:--|--:|
| `w-one` | 0.0625 | `0x00BF4010` |
| `w-two` | 0.0625, 0.125 | `0x00BF4030` |
| `w-three` | 0.0625, 0.125, 0.25 | `0x00BF4070` |
| `w-rev` | 0.0625, 0.125 in slots 2, 3 | `0x00BF4030` |
| `w-same` | 0.25, 0.25 (same uniform) | `0x00BF4040` |
| `w-same-value` | 0.25, 0.25 (different uniforms) | `0x00BF4040` |
| `w-same-half` | 0.5, 0.5 | `0x00BF407F` |
| `w-same-half-const` | 0.5, 0.5 (same uniform) | `0x00BF407F` |
| `w-three-same` | 0.25, 0.25, 0.25 | `0x00BF4040` |
| `w-shape` | 0.25, 0.25 in different operand positions | `0x00BF4040` |
| `w-or-25-75` | 0.25, 0.75 | `0x00BF40BF` |
| `w-or-50-75` | 0.5, 0.75 | `0x00BF40BF` |
| `w-halves` | 0.25 to `.l*`, 0.5 to `.*h` | `0x00BF7F40` |
| `w-mul` | `MAD` 0.25 low; `MUL` 0.5 low and 0.25 high | `0x00BF40BF` |

The stored bytes are consistent with each slot **ORing its fx10 code** into the
destination half, not adding: the codes are `value*256` (0.0625 = `0x10`,
0.125 = `0x20`, 0.25 = `0x40`, 0.5 = `0x80`, 0.75 = `0xC0`) and the store
scales the code to a byte (`0x80` reads `0x7F`, `0xC0` reads `0xBF`). Then
`0x40 | 0x80 = 0xC0` reads 0.75, while adding would read 1.0; two 0.25 writes
OR to `0x40` and read 0.25, while adding would read 0.5. `w-one` shows the
packet's write replaces the 0.25 prime rather than ORing with it (`0x10`, not
`0x50`), so the OR is only among the slots of the current packet. `w-rev` shows
the order does not matter. This is inferred from the byte; the direct
measurement is the word, and the fp20 (`.lh`) destination is not covered.

### ALUN result registers read zero

`--set result-regs` (13 variants) from `tests/grate/asm/alu_result_regs.in`,

sit in the producer's packet, one packet later, or two packets later. Packets
0, 1 and 2 write 0.0625, 0.125 and 0.5 through slot 1 (and 0.25 in packet 2's
slot 0), so a readback would name the packet it came from. The reader is

| variants | r3.lo (the read) | word |
|:--|--:|--:|
| `r-same-s2`, `r-before-s0`, `r-alu0-same`, `r-alu3-same`, `r-next-s0`, `r-next-s2`, `r-alu0-next`, `r-none`, `r-send-next`, `r-recv-next` | 0.0 | `0x000000xx` (r2 carries the packet's write) |
| `r-fp20`, `r-fp20-h`, `r-fp20-l` | 0.0 | `0x0000EF00` |

## 10. The linker, TRAM and the varying fetch

`asm_characterize.tram.json` (40 variants), templates `asm/tram_linker.in` and
`asm/tram_fs.in`, vertex shaders `asm/vs_tram.txt` (exports
`(0.25, 0.5, 0.75, 0.875)`), `vs_tram_hi.txt` (blue 1.5) and `vs_tram_b.txt`
(the reversed vector). The vertex shader exports register 7, the second enabled
export, and the linker names it `export1`. Each variant replaces the whole LINK
instruction and the fetch/readout fields; the fragment is four batches:

    batch 0   prime r0..r3 with fp20 constants 0.0625, 0.125, 0.375, 0.625
    batch 1   one MFU word: sfu rcp r4, the two barycentric multipliers, ipl
    batch 2   convert the two fetched registers to fx10 with `.l*`
    batch 3   store r2, r3

Every vertex exports the same vector, so interpolation is the identity and the
sample point cannot change the result. The stored word is `r3 << 16 | r2` and
the low byte of each half is the linear value. The upper bits of a half are not
written by the `.l*` conversion: they carry whatever the destination held
before (the fp20 source's high bits or the prime), so only the low byte is a
value. For example `0xEB40` is 0.25 with `0xEB` left over.

### The four letters are per-column destinations

The k-th letter of `tramN.swizzle` is the TRAM component that export component
k is copied to, and the k-th format is how it is converted. The constant vector
is `(40, 7F, BF, DF)` in the linear byte, so a readback names the mapping:

| LINK swizzle | TRAM readback (x, y, z, w) | words (xy, zw) |
|:--|:--|:--|
| `xyzw` | (0.25, 0.5, 0.75, 0.875) | `0xF17FEB40`, `0xF5DFF3BF` |
| `yxzw` | (0.5, 0.25, 0.75, 0.875) | `0xF140EB7F`, `0xF5DFF3BF` |
| `wzyx` | (0.875, 0.75, 0.5, 0.25) | `0xF1BFEBDF`, `0xE740EF7F` |
| `xyxx` | (0.875, 0.5, --, --) | `0xF17FEBDF` |
| `xxzw` | (--, --, 0.75, 0.875) | `0xF5DFF3BF` |

`xyxx` writes tram.x three times (export.x, then export.z, then export.w) and
the last column wins; tram.y is export.y. `xxzw` writes x twice and leaves y
out. Both are fully written in the components they read, so neither depends on
state from an earlier draw. `tram1.xyzw` with `ipl: t1...` gives the same words
as row 0, so the row index is the fetch's `tN` prefix.

### `exportM` is the enabled-export slot, not the register number

The vertex shader enables exports 0 (`gl_Position`) and 7 (`vcolor`) and writes
the constant to register 7. `LINK ..., export1` copies the constant, while
`export0` copies the position: xy reads `0xF100EB00` (x and y both 0 after the
conversion) and zw reads `0xF7FF0000` (z = 0, w = 1.0). The 1.0 alpha identifies
the position and rules out the constant (0.875). So the linker's export index
counts the enabled exports, 0 and 1, rather than the register numbers 0 and 7.

### Fetch controls, NOP and persistence

| variant | word | reading |
|:--|--:|:--|
| `fetch-nop-x` | `0xF17FEB10` | x is the 0.0625 prime (`0x10`), y is 0.5 |
| `fetch-nop-w` | `0xF19FF3BF` | z is 0.75, w is the 0.625 prime (`0x9F`) |
| `fetch-sat-nop-w` | `0x0000F3BF` | z is 0.75, w is 0.0, not the prime |

An `ipl` operand of `NOP` leaves that row register alone, as the syntax says.
`sat(NOP)` does not: it writes 0.0 to the register, so it is a real write of a
zero with the saturate flag set, not "no fetch" with a modifier.

A *linker* NOP column is different again: it does not write the TRAM component,
and the component then keeps the previous draw's value. The persistence pair
runs in this order: `persist-first` fills the whole row from
`(0.25, 0.5, 0.75, 0.875)` and reads xy as `0xF17FEB40`; `persist-keep` then
uses the reversed export `(0.875, 0.75, 0.5, 0.25)` but its LINK writes only
tram.y. The readback is `0xF1BFEB40`: x is still 0.25 from the first draw and y
is the new 0.75. The TRAM row is not cleared between draws on this setup; it
even survives between assembler invocations, because the second program sees
the first's row. That is why the `map-dup` variants above were chosen to read
only components their own LINK writes.

### Saturate on the fetch

`vs_tram_hi.txt` writes blue 1.5. `unsat-z` reads back `0xF3BFFBFF` and
`sat-z` `0xF3BFF7FF`: the low byte is `0xFF` in both, because the fx10
conversion of anything above 1.0 reads as 1.0 at the byte level, but the
unconverted field keeps the fetched fp20, whose high byte is `0xFB` for 1.5
and `0xF7` for 1.0. So the saturate modifier clamps the value in the row
register to 1.0; the 0..1 byte readout alone cannot show it. `sat-x` (0.25,
in range) equals the no-sat word `0xF17FEB40`.

### Interpolation disable

On the constant varying, `fp20 (dis)` on x changes nothing (`dis-const` =
`0xF17FEB40`). On the coloured quad, the interpolated blue at the first pixel
is `0x01`; with `fp20 (dis)` on the blue column the same read is `0x00`
(`nodis-color` `0xF7FFAF01` against `dis-color` `0xF7FF0000`), and alpha is
unchanged. So the modifier replaces that component's interpolated value with a
vertex value. Which vertex is not determined by this single sample.

### fx10 linker formats and the fx10 fetch

| variant | word | reading |
|:--|--:|:--|
| `fmt-low-fx10` | `0x007F0040` | r0 = `0040` (0.25 low, 0 high), r1 = `007F` (0.5 low, 0 high) |
| `fmt-high-fx10` | `0x7F7F4040` | r0 = `4040`, r1 = `7F7F` (both halves hold the value) |
| `fmt-low-fx10-zw` | `0xDFDFBFBF` | r2 = `BFBF`, r3 = `DFDF` |
| `fmt-low-fp20` | `0xF100EB00` | reading an `fx10.l` component as fp20 converts to 0.0 |
| `fmt-fp20-fx10` | `0x00000000` | an `.fx10` fetch of fp20 components reads 0 in both halves |

The `.fx10` fetch does not produce the documented "two fixed10 values in one
row register" in a way these words settle: `fx10.l` gives (value, 0) while
`fx10.h` gives (value, value), and reading a component written by the other
format gives zero. The half layout is left unresolved rather than fitted.

### The `(z)` magic write

The modifier sets bit 0 of the linker instruction's first word: `z-base` is
`0x00000009` where the same LINK without `(z)` is `0x00000008`, and the
disassembler reads the bit back. The documented effect - a write of VEC4.z to
TRAM0.w - is not what the hardware does here:

| variant | word | reading |
|:--|--:|:--|
| `z-base` (`xyzw`, all fp20, `(z)`) | `0x00000000` | all four components read 0 |
| `z-base-xy` | `0xF100EB00` | x and y also read 0 |
| `z-swizzle` (`wzyx`, `(z)`) | `0x00000000` | swizzle does not change it |
| `z-export0` (`export0`, `(z)`) | `0x00000000` | the export does not change it |
| `z-row1` (`tram1`, `(z)`) | `0x00000000` | the row does not change it |
| `z-alive` (no fetch, stores 0.25/0.75) | `0xF1BFEB40` | the draw ran; the zeros are reads |
| `z-two-step` (normal, then NOP-column `(z)`) | `0xF5DFF3BF` | the z word changes nothing |
| `z-two-step-rev` (`(z)` first, then normal) | `0xF5DFF3BF` | the normal word wins |
| `z-nop-w` (w column NOP, `(z)`) | `0xF5DF0000` | z is 0, w keeps the previous 0.875 |

`z-alive` rules out a dropped draw: the same `(z)` linker with a fragment that
does not fetch stores `0xF1BFEB40`. `z-nop-w` shows the three fp20 columns each
wrote 0.0 while the NOP column still skipped. The consistent reading is that
`(z)` switches the link's source from the named export to a VEC4.z input, and
that input is zero in these programs - nothing here populates it. What exactly
that input is, and how a program is supposed to fill it so the fragment z path
works, is unresolved. A second LINK instruction with `(z)` and all-NOP columns
does not perform the write either.

### What this set does not settle

* how VEC4.z is supplied, or which vertex program state the `(z)` bit selects;
* why an `fx10.l` fetch gives a zero high half while `fx10.h` duplicates the
  value into both halves;
* what happens with more than one TRAM row in use, or with TEX between the
  fetch and the read;
* persistence across a real application's frames: here it is observed between
  consecutive assembler invocations on the same board, which is enough to
  confound a test but is not the same as a frame-to-frame guarantee;
* the vertex the `(dis)` modifier picks, which one colour sample cannot name.

variants, three repeats, plus the four control rows), pinned from

## 11. The TEX instruction

`asm_characterize.tex.json` (60 variants), template `asm/tex_probe.in`. The
program writes the four coordinate/LOD registers as fp20 in batch 0, fetches in
batch 1, optionally fetches again in batch 2 and then runs an ALU packet, and
stores `r2`/`r3` in batch 3. Variants set the texture size, format, pitch and a
second sampler through the harness (`GRATE_TEX_*`), and `--mipmap` where the
fetch is supposed to see a mip chain. The word is the RGBA8888 surface word:
`store rt1, r2, r3` of a fetched texel reproduces the texture's word exactly,
so a row colour comes back as the same `0x0000FF00`-style word it was written
as.

### Sensitivity controls

| variant | word |
|:--|--:|
| `ctl-white` (s = 0.875) | `0xFFFFFFFF` |
| `ctl-black` (s = 0.125) | `0x00000000` |
| `ctl-row0` (`GRATE_TEX_ROWCOLOR`, t = 0.125) | `0x000000FF` |
| `ctl-row1` (t = 0.375) | `0x0000FF00` |
| `ctl-row3` (t = 0.875) | `0xFFFFFFFF` |

The five differ, so a fetch that changes the texel, the row or the level shows
up in the word. `t` walks rows linearly and `s` selects the half.

### Sampler index and the enable bit

`idx1-white` and `idx1-black` both read `0x000000FF`: sampler index 1 is the
`GRATE_TEX2` surface, which is a uniform `0x000000FF`, and changing `s` cannot
change it. So bits 0..3 really do select a sampler rather than an offset into
one texture.

Indexes with nothing bound are not a clean "no texture" answer. With only
textures 0 and 1 in the context:

| word | index 2 | index 3 | index 5 | index 15 |
|:--|--:|--:|--:|--:|
| `s = 0.125` | `0xFFFFFFFF` | `0xFF000000` | `0x00FFFFFF` | `0xFFFFFFF8` |

The values look like whatever the descriptor table holds beyond the bound
entries, not a defined fill. Only indexes 0 and 1 are meaningful in this
harness; the rest are recorded, not interpreted.

Clearing bit 10 (`en-off`, word `0x00001020`) leaves the destination registers
untouched: they still hold the fp20 prime `0.75` (`0xF300F300`), even when `s`
is 0.875 and an enabled fetch would return white (`en-off-white` is the same
word). The enabled control `en-on-prime` is `0x00000000`, so the fetch did not
run, rather than running and writing zero.

### Destinations, coordinates and the "unknown" bits

Bit 5 moves the destination pair: `dest-r0r1` (bit 5 clear, `store rt1, r0,
r1`) reads `0xFFFFFFFF` while the same white sample through `r2`/`r3` also
reads `0xFFFFFFFF`, so the bit moves the data but this sample cannot name the
channel order on that path. The order through `r2`/`r3` is the surface word's.
Section 15 settles the order on both pairs with a surface that carries one
channel per texel and a four-distinct-byte word: neither pair reorders.

Bit 4 moves the coordinate registers: `sel-t` (bit 4 set, `s` from `r2`, `t`
from `r3`) reads `0x000000FF` and `sel-t-control` (same constants, bit 4 clear,
`t` from `r1`) reads `0x00FF0000`. Since only bit 4 and the register that holds
`t` differ, the select is real. `sel-s` reads `0x00000000`: with bit 4 set the
`S` constant (written to `r0`) is ignored and `s` comes from `r2`'s `0.125`.

Bits 6..9 and 11 are inert on every base measured. On the sampler-1 fetch each
one leaves `0x000000FF` unchanged, and on an explicit-LOD fetch at levels 0, 1
and 2 each one returns the same word as its base (`0xFFFFFFFF`, `0x00000000`,
`0x00545454`). An earlier run appeared to change the level-1 answer; it had
been assembled without `--mipmap`, so it sampled level 0 and proved nothing.
The corrected measurement is the one in the table. Bits 14..31 were already
measured inert by `probe_tex_unknown.sh`; this set does not revisit them.

### Wrapping and dimension

The default wrap is **repeat**, not clamp or mirrored repeat:

| variant | word | reading |
|:--|--:|:--|
| `wrap-s125` (s = 1.25) | `0x00000000` | 1.25 -> 0.25, black half |
| `wrap-sn025` (s = -0.25) | `0xFFFFFFFF` | -0.25 -> 0.75, white half |
| `wrap-s225` (s = 2.25) | `0x00000000` | 2.25 -> 0.25 |
| `wrap-t125` (t = 1.25) | `0x0000FF00` | 1.25 -> 0.25, row 1 |
| `wrap-tn025` (t = -0.25) | `0xFFFFFFFF` | -0.25 -> 0.75, row 3 |

Clamp would give white for `wrap-s125` and row 3 for `wrap-t125`; mirrored
repeat would give white for `wrap-s125`. The measured values are the repeat
ones.

A 64x64 surface (`size64-l0`) still samples the two-tone image, and an 8x8
surface with explicit LOD 1 (`size8-lod1`, `--mipmap`) reads `0xFFABABAB`, the
mixed 4x4 level. So the sampler follows the texture's own dimension and mip
chain rather than a fixed 4x4.

`pitch64` and `pitch32` allocate the 4x4 surface with a 32- or 64-byte row
pitch while the data is written through that pitch. At `t = 0.375` the natural
allocation returns row 1 (`0x0000FF00`) but both pitched allocations return
`0x00000000`. The sampler therefore walks rows at `width * 4` bytes and has no
pitch field: a different pitch shears the fetch into the padding.

### Block-compressed formats

A 16x16 DXT1 surface has four block rows, each filled with one solid colour:

| variant | word |
|:--|--:|
| `dxt1-16-r0` | `0xFF0000FF` |
| `dxt1-16-r1` | `0xFF00FF00` |
| `dxt1-16-r2` | `0xFFFF0000` |
| `dxt1-16-r3` | `0xFFFFFFFF` |

So block addressing works and `t` selects the block row. The alpha byte is
`0xFF` in every row, including the row whose stored word had none, which is
DXT1's 1-bit alpha decoding as opaque. ETC1 gives the same cycle with a small
decoding difference: `etc1-4-block` reads `0xFF0000FD` where DXT1 reads
`0xFF0000FF`. A zero DXT1 block (`dxt1-zero`) reads `0xFF000000`, again with
opaque alpha.

### LOD, bias and explicit level

On the 4x4 chain at `s = t = 0.5`:

| variant | LOD register | bits 12/13 | word |
|:--|--:|:--|--:|
| `lod-neg` | -1 | 1/0 | `0xFFFFFFFF` (clamped to level 0) |
| `lod0` | 0 | 1/0 | `0xFFFFFFFF` |
| `lod1` | 1 | 1/0 | `0x00000000` |
| `lod-half` | 1.5 | 1/0 | `0x00000000` (nearest mip) |
| `lod2` | 2 | 1/0 | `0x00545454` |
| `lod3` | 3 | 1/0 | `0x00545454` |
| `lod9` | 9 | 1/0 | `0x00545454` (clamped) |
| `lod-est` | 2 | 0/0 | `0xFFFFFFFF` (register ignored, estimate used) |

The chain's level contents at the centre are: level 0 white, level 1 black,
level 2 the flat `0x54`. Fractional levels round to a neighbour, which matches
the harness's `NEAREST_MIPMAP_NEAREST` filter.

Bias and explicit LOD are different mechanisms, and on a 16x16 chain with the
same register they select different levels:

| variant | bits 12/13 | LOD | word |
|:--|:--|--:|--:|
| `bias0-16` | 1/0 | 0 | `0xFFFFFFFF` |
| `expl0-16` | 0/1 | 0 | `0xFFFFFFFF` |
| `bias3-16` | 1/0 | 3 | `0xFFABABAB` |
| `expl3-16` | 0/1 | 3 | `0x00000000` |
| `both3-16` | 1/1 | 3 | `0xFFABABAB` |

`0xFFABABAB` is the averaged level (0xAB = 171/255); `expl3-16` lands on a
different one. `both3-16` equals the bias word, so **bias wins when both bits
are set**, which is what the current reference says. On the 4x4 chain
`bias3-4` and `expl3-4` are both `0x00545454`, so that size cannot separate
them; only 16x16 does, which also means the derivative estimate there is not
zero. The estimate is not fitted from these three points - the follow-up is a
size sweep, not a single guess.

### What this set does not settle

* what an unbound sampler index reads, and whether the four different words
  come from descriptor memory or from an address alias;
* the channel order on the `r0`/`r1` destination path: separating it from the
  DW's own register pairing needs a texture with four distinct channels, and
  the harness only produces uniform rows;
* the exact LOD estimate - `bias3-16` proves it is not zero but three points
  cannot name it;
* linear filtering and mip filtering: the harness always sets the magnitude
  filter to `NEAREST` and the mip filter to `NEAREST_MIPMAP_NEAREST`, so no
  bit or coordinate in this set can show a blend;
* cube maps and shadow samplers, which have no binding path in the harness;
* why ETC1's low byte is `0xFD` where DXT1's is `0xFF` for the same block
  colour, which is a decoder difference rather than an instruction effect.

## 12. The PSEQ fetch

`asm_characterize.pseq.json` (27 variants), template `asm/pseq_probe.in`. Five
batches:

    batch 0  r0 = (0x40, 0x80), r1 = (0x60, 0xA0), store to the target   [A]
    batch 1  overwrite r0/r1 with (0xC0, 0x20), (0x30, 0x70)              [B]
    batch 2  r2 = (0x10, 0x50), r3 = (0x8F, 0xCF)                         [C]
    batch 3  the PSEQ fetch
    batch 4  an optional second store

The DW converts each fx10 half to a byte, so the three answers are distinct:
a working fetch into r0/r1 stores `0x9F607F40`, a suppressed one stores
`0x703020BF`, and a fetch that returned zero would store `0x00000000`. The
program writes pattern A to the target and to the same pixel it later reads, so
the round trip is self-contained.

### Enable bits and the destination pair

| variant | word | reading |
|:--|--:|:--|
| `ctl-nofetch` | `0x703020BF` | pattern B, no fetch |
| `ctl-fetch` | `0x9F607F40` | pattern A, rt1 fetched |
| `ctl-mnemonic` | `0x9F607F40` | `load rt1, r0, r1` is the same word |
| `en-b3-clear` | `0x703020BF` | bit 3 alone is required |
| `en-b23-clear` | `0x703020BF` | bit 23 alone is required |
| `pair-23` | `0x9F607F40` | bit 1 puts the fetch in r2/r3; the r2/r3 store reads A |
| `pair-23-no23` | `0x703020BF` | with bit 1 set the r0/r1 store still reads B |
| `pair-01-store23` | `0xCF8F5010` | without bit 1 the r2/r3 store reads C |

So bits 3 and 23 are two required enables, not one flag with a spare bit, and
bit 1 really moves the destination pair: nothing is written to the other pair.

### Targets and the index field

`idx-3-coverage` (with `GRATE_COVERAGE`), `idx-4-rt4` (`GRATE_RT4`) and
`idx-5-rt5` (`GRATE_RT5`) all return `0x9F607F40`: the fetch reads the target
named by bits 16..19, and a coverage, colour or extra surface all round-trip.
`fmt-rgba8888` is the same word, so the index and not the class selects the
surface.

Indexes with nothing bound are not a defined value. Two runs of index 0 gave
`0x7030FF00` and `0x703000FF`; index 2 gave `0x7030FFFF` and `0x7030047F`;
index 15 gave `0xFFFFFFFF`. The partial words (only r0 written, r1 still B)
suggest a narrower surface behind those descriptors, but the values are not
stable across runs, so they are recorded as undefined and left out of the
pinned set.

### Render target formats

The store/target pair is rt5 with `GRATE_RT5_FMT`:

| format | word | reading |
|:--|--:|:--|
| `rgba8888` | `0x9F607F40` | pattern A, unchanged |
| `a8` | `0x9F000000` | only the fourth component survives, in r1.hi |
| `l8` | `0xFF404040` | first component (0x40) in RGB, alpha 1.0 |
| `rgb565` | `0xFF637E42` | R 0x42, G 0x7E, B 0x63, A 0xFF |

The pattern's four bytes are `0x40, 0x7F, 0x60, 0x9F` in r0.lo, r0.hi, r1.lo,
r1.hi, so the formats name the channel order as **R, G, B, A**: A8 keeps byte 3
(alpha) and zeroes the rest, L8 keeps byte 0 and replicates it as luminance with
alpha 1.0, and RGB565 keeps bytes 0..2 quantised to 5/6/5 and replaces alpha
with 1.0. The 5/6/5 expansion is exact for these inputs: `0x40 -> 0x42`,
`0x7F -> 0x7E`, `0x60 -> 0x63`, which is `v >> 3`, `v >> 2`, `v >> 3` scaled
back to 8 bits. A narrow surface therefore does not return the stored byte in
the same component for A8/L8; the fetch maps it into the RGBA channels.

### Bits and the spill form

On the a8 surface, each of bits 4, 5, 6, 7, 8, 11, 15, 20, 22, 25 and 31 leaves
`0x9F000000` unchanged. That is the configuration where a write mask, sub-word
select or format field would be visible, so those bits carry no such meaning
for the fetch; it agrees with the earlier sweep on rgba8888, now on a surface
where a mask would matter.

Bit 24 (with bit 23 set, the spill form) is **not** a plain suppression:
`spill-b24` reads `0x003020BF`, pattern B with byte 3 (r1.hi) zeroed. The
normal fetch does not happen, but one component is written, so the spill form
has a write mask over the low word and is a different instruction rather than
"fetch off".

### What this set does not settle

* **Addressing at all.** Every fragment stores the same word, so a fetch that
  read a different pixel would return the same value. The round trip proves the
  index, the enable bits and the pair, not that the fetch uses the fragment's
  own position. The smallest follow-up is a program that stores a
  position-dependent value (the pixel x or y from the MFU) and fetches it back
  across a 64x64 window; a wrong address then shows as the wrong column. Section 14 answers this: the
  map is the identity.
* What index 0 and 2 read: the values are unstable and the partial write
  pattern is not explained.
* The spill form's fields: bit 24 overlays the low word, and this set only
  shows that one component is zeroed.
* Alignment and offsets: rt5 is allocated at `width * bpp` and the fetch has no
  pitch field of its own in this harness, so a pitched or tiled target is not
  covered.
* Whether the fetch samples the same *frame*: the program's own store is
  visible to a later batch, which this set confirms, but a frame-to-frame
  guarantee is not measured.

## 13. ALU control: CSEL, condition codes and send

`asm_characterize.alu_control.json` (30 variants), template
`asm/alu_control.in`. Three packets, four scalar slots each, with an MFU and a
TEX slot before the ALU in the last two packets. The primes put 0.25 in `r2.lo`
and 0.75 in `r3.lo`; a consumer writes `r3.l*` so the stored word is
`r3 << 16 | r2` after the DW conversion, and an unwritten register still reads
its prime.

### CSEL

`CSEL` is `(rA*rB < 0) ? rB : (rC*rD)` on this hardware, with three
refinements the earlier three-row table did not fix:

| variant | operands | word | reading |
|:--|:--|--:|:--|
| `csel-base` | 0.25*1 vs 0.75*1 | `0x00BF0000` | 0.75 - positive product takes rC*rD |
| `csel-pos` | 0.5*1 vs 0.25*1 | `0x00400000` | 0.25 - the positive branch |
| `csel-neg-rb` | -0.25*0.5 vs 0.75*1 | `0x007F0000` | 0.5 = **rB**, not rA*rB (-0.125 -> 0) |
| `csel-neg-a` | -0.25*1 vs 0.75*1 | `0x00FF0000` | 1.0 = rB again |
| `csel-zero` | 0*0.5 vs 0.75*1 | `0x00BF0000` | 0.75 - a **zero product takes the false branch** |
| `csel-rd-off` | rD omitted | `0x00BF0000` | same as rD = 1.0: rC is used as-is |
| `csel-rd-one` | rD = #1 | `0x00BF0000` | rC*1 |
| `csel-cc-eq` | positive result, `(eq)` | `0x00000000` | the condition post-processes CSEL like any ALU result: 0.75 != 0 -> 0 |
| `csel-cc-gt` | positive result, `(gt)` | `0x00FF0000` | 0.75 > 0 -> 1.0 |

Two grammar facts fall out of this: the fourth operand can only be the constant
`#1` (a uniform or register there is "Invalid src register"), and `#0` in that
position is the same error - disabling rD means omitting it. So a backend can
only choose between `rC` and `rC*1`, which are the same value; the only useful
fourth operand is none.

### Condition codes and registers

| variant | arrangement | word | reading |
|:--|:--|--:|:--|
| `cr-next` | write cr0, read in the next packet | `0x00FF0000` | 1.0 - `result != 0` |
| `cr-same` | write and read in one packet | `0x00000000` | 0.0 - needs a packet boundary |
| `cr-pair-low` | write cr0, read cr1 | `0x00000000` | cr0 and cr1 are independent |
| `cr-pair-high` | write cr1, read cr1 | `0x00FF0000` | the high sub-register is addressable |
| `cr-two-slots` | slot 0 writes cr2, slot 1 writes cr4, next packet reads cr2 | `0x00FF0000` | two slots write two registers without interference |
| `cr-cond-write` | `(eq)` on a non-zero result, then read | `0x00000000` | the condition is stored as 0, not the value |

The condition modifier on a CSEL or a CR write behaves exactly as on a
row-register destination: it replaces the result with the 0/1 predicate, and
the same-packet read still returns 0.

### Send and receive

The receiver's accumulator is the **immediately preceding slot's** result, and
nothing crosses a packet boundary:

| variant | arrangement | word | reading |
|:--|:--|--:|:--|
| `send-two` | slot 0 sends 0.25, slot 1 sends 0.5, slot 2 receives | `0x008F00BF` | receiver 0.5625 = 0.0625 + 0.5; r2 = 0.75 = the two writes ORed |
| `send-min` | slot 0 `MIN(0.25, 0.75)` sends, slot 1 receives | `0x00500040` | receiver 0.3125 = 0.0625 + 0.25; r2 = the MIN result |
| `send-last-then-recv` | slot 3 sends, next packet's slot 0 receives | `0x001000FF` | receiver 0.0625 - no accumulator across the packet |

Those three are the parts that reduce to a rule. The rest are recorded raw
because the value a sender writes to its own destination is not its plain
operand once either bit is set:

| variant | word |
|:--|--:|
| `send-three` (three senders, receiver in slot 3) | `0x00CF00FF` |
| `send-before` (receiver in slot 0, sender in slot 1) | `0x00CF00BF` |
| `send-mul` (`MUL(0.25, 1, 0.5)` sends, then a receiver) | `0x00507F40` |

`send-three` reads receiver 0.8125 = 0.0625 + 0.75 (the last sender's result)
while its r2 is 1.0, which is not the OR of 0.25, 0.5 and 0.75; the send bits
evidently also change what a producer writes to its own destination. `send-mul`
sends 0.25 (the product) but its destination holds 0.5. Fitting either would
need a variant per slot with one bit at a time, which this set does not have.

**`send-before` does not reproduce the existing note that reversing the order
transfers nothing.** With the receiver in slot 0 and the sender in slot 1 of
the same packet, the receiver reads 0.8125 = 0.0625 + 0.75, i.e. it did get the
sender's value. The older measurement used a different rC and destination, so
the two arrangements are not directly comparable - this is a review point, not
a settled contradiction.

### Several writers to an fp20 destination

The fx10 OR is not specific to the fx10 format: **fp20 destinations OR too**.

| variant | word | reading |
|:--|--:|:--|
| `fw-two` (0.25 then 0.75, both `.lh`) | `0x0000FB00` | 0xEB00 OR 0xF300 = 0xFB00 |
| `fw-three` (0.0625, 0.25, 0.75, all `.lh`) | `0x0000FB00` | the same OR, the low value already contained |
| `fw-fx10-two` (0.25 then 0.75, `.l*`) | `0x000000BF` | the known fx10 OR, 0x40 OR 0xC0 = 0xC0 -> 0.75 |
| `fw-lh-then-fx10` | `0x0000E7BF` | a mixed write; neither format alone explains 0xE7 |
| `fw-lh-then-high` | `0x0000E700` | `.lh` then `.*h`: the high byte is 0xE7, not the fp20 0xF3 |

So the OR is a property of the destination half, not of the fx10 format, and
the two-format combinations are recorded but not explained.

### Intervening stages

| variant | arrangement | word | reading |
|:--|:--|--:|:--|
| `mfu-between` | producer 0.5, then `sfu: rcp r5` in the next packet, then the consumer | `0x007F007F` | 0.5 survives; an SFU write to another register does not disturb it |
| `tex-between` | producer 0.5, then a TEX into r0/r1, then the consumer of r2 | `0x007F007F` | 0.5 survives; the fetch does not clobber r2 |
| `tex-clobber` | producer 0.5, then a TEX into r2/r3, then the consumer of r2 | `0x00000000` | the fetch is the new writer; the consumer sees the texel |
| `mfu-clobber` | producer 0.5, then `sfu: rcp r2`, then the consumer | `0x0000FF00` | the consumer's result is 0.0 while r2 reads 0xFF00; the SFU write changes the consumer's answer, and the exact value it leaves is not fitted |

TEX results are already known to be visible to the ALU in the same batch; this
set only adds that a *later* TEX and a later MFU do not break a row-register
dependency unless they write the same register.

### `aluN` writes

The earlier forwarding set measured `alu0..3` as sources in 13 arrangements:
every one read 0.0, including in the producer's own packet. This set adds
nothing there, because **the assembler grammar has no `aluN` destination**:
`ALU_DST_REG` accepts row registers 0..15, globals, the 0/1 constant and
uniforms, and the result registers exist only in the source rule. A raw word
with `dst_reg` = 24..27 could still be tested - that is the smallest useful
follow-up, and it needs a dumped word bit-patched rather than a new mnemonic.

### What this set does not settle

* the send bits' effect on the sender's own destination: `send-three`,
  `send-before` and `send-mul` are raw, and `send-before` conflicts with the
  older "reverse order transfers nothing" note;
* the mixed fp20/fx10 writers (`fw-lh-then-*`), whose high byte is neither
  format's value;
* what value an SFU op leaves in a row register (`mfu-clobber`: consumer 0.0
  while the word shows 0xFF00);
* whether `aluN` accepts a destination at all;
* CSEL with a negative `rC*rD` or a negative zero: the false branch was only
  exercised with positive operands.

### Recorded runs

`tests/grate/asm/results/pin-alu-control` and `verify-alu-control` hold 94 rows
each (30 variants, three repeats, plus the controls), pinned from
`32226d2a8542...` to `45cc01a536b2...`. Re-pinning from the pin directory is
byte-identical.

## 14. PSEQ addressing: which pixel the fetch reads

`asm_characterize.pseq_addr.json` (18 variants), template `asm/pseq_addr.in`,
vertex shader `asm/vs_scale_offset.txt`. Section 12 could not see the address
because every pixel stored the same word. Here each fragment tags its own
pixel with its position:

    R = frag.x + 1    G = frag.y + 1    B = 0x9F    A = 0xBF

The tag is unique for coordinates below 96 and differs from pattern B
(`0x9F607F40`), pattern C (`0x10703020`) and zero. Batch 1 stores the tag to
the fetch target, batch 2 overwrites r0/r1 with B, batch 3 sets C and can
optionally store it, batch 4 fetches, batch 5 stores the fetched word to the
linear rt4 surface. The new opt-in readback `GRATE_REGION=x,y,w,h` (commit
`2566b55`) prints that rectangle row by row and reports a 32-bit digest of it
as the result word, so the whole map is pinned instead of `fb_data[0]`.

The quad is 64x64 pixels, placed with the "offset" uniform of
`vs_scale_offset.txt`; the target itself is still the harness's 256x256
surface, so this exercises a 64x64 *area*, not a 64x64 allocation.

### The position registers

`diag-pos` stores `posx - 8192` in R and `posy - 8192` in G (A and B keep the
markers):

| target row | first word | last word |
|--:|:--|:--|
| 0 | `BF9F0000` | `BF9F003F` |
| 63 | `BF9F3F00` | `BF9F3F3F` |

So `posx - 8192` is the window column and `posy - 8192` is the window row, with
the row counted from the bottom of the viewport: the quad spans NDC y -1..-0.5
and filled target rows 0..63. That is consistent with the documented
`8192 + (height - 1) - y` form read with y counted down from the top; it does
not fit a bottom-up y in that formula.

Batch 0 of the template splits the position read into its own packet because
an ALU write to one half is carried out in that half's fx10 format, and
`8192 + x` does not fit fx10. The first attempt computed the tag directly from
`posx` and every coordinate saturated to `0xFF`.

### The fetch map

| variant | picture | digest |
|:--|:--|--:|
| `diag-pos` | posx-8192, posy-8192 | `0xE2AECDC5` |
| `tag-nofetch` | the tags (reference) | `0xFDFE7DC5` |
| `ctl-nofetch` | B everywhere, fetch NOP | `0x8086DDC5` |
| `ctl-zeros` | the tag store writes zeros | `0x76EFDDC5` |
| `tag-fetch` | the fetch map | `0xFDFE7DC5` |
| `last-store` | C stored over the tag before the fetch | `0x54FFDDC5` |
| `pair-23` | fetch into r2/r3, stored from r2/r3 | `0xFDFE7DC5` |
| `src-rt1` | framebuffer, tiled 16x16 | `0xFDFE7DC5` |
| `src-rt3-linear` | coverage target, linear | `0xFDFE7DC5` |
| `src-rt3-tiled` | coverage target, tiled 16x16 | `0xFDFE7DC5` |
| `src-rt3-tiled-off` | as above, quad at x=8,y=8 | `0x97279DC5` |
| `src-rt5-rgb565` | rt5, rgb565 | `0xAB4CFDC5` |
| `src-rt5-a8-x` | rt5, a8, tag in the A byte | `0x4CEFDDC5` |
| `src-rt5-a8-y` | as above, y in the A byte | `0x00EFDDC5` |
| `src-rt5-l8-x` | rt5, l8, tag in the R byte | `0xDF583DC5` |
| `src-rt5-l8-y` | as above, y in the R byte | `0x338C9BC5` |
| `off-32-16` | quad at x=32,y=16 | `0x88E83DC5` |
| `off-1-0` | quad at x=1,y=0 | `0x0E494C85` |

`tag-fetch` and `tag-nofetch` have the same digest: the fetch returned, at every
pixel, exactly the tag that pixel had stored.

| target row | words (first, second, ... last) |
|--:|:--|
| 0 | `BF9F0101` `BF9F0102` ... `BF9F0140` |
| 1 | `BF9F0201` `BF9F0202` ... `BF9F0240` |
| 63 | `BF9F4001` `BF9F4002` ... `BF9F4040` |

The two dead-fetch pictures say the same thing from the other side:
`ctl-nofetch` is `9F607F40` in every word and `ctl-zeros` is `00000000`
everywhere (`nz=0`). A fetch that did not happen therefore cannot be mistaken
for a fetch that returned the tag, and the fetched bytes come from the surface,
not from the registers.

`last-store` puts pattern C on the surface in the packet before the fetch; the
whole map is `10703020`. The fetch reads the surface at the fragment's position
and sees a store issued one packet earlier - it is not returning the fragment's
own earlier store or the current r0/r1 (B).

`pair-23` has the `tag-fetch` digest: setting bit 1 moves the fetched word to
r2/r3 (stored from there) without changing the address.

### Surfaces, layouts and pitches

The same tags, written and fetched through five different surfaces, all return
the tag the fragment stored:

| variant | row 0 | reading |
|:--|:--|:--|
| `src-rt1` | `BF9F0101` ... `BF9F0140` | tiled framebuffer, identity |
| `src-rt3-linear` | `BF9F0101` ... `BF9F0140` | linear target, identity |
| `src-rt3-tiled` | `BF9F0101` ... `BF9F0140` | tiled target, identity |
| `src-rt3-tiled-off` | `BF9F0909` ... `BF9F0948` | quad at 8,8: R=9 (x=8), G=9 (y=8), last `BF9F4848` = x=71,y=71 |

So the fetch's byte address is the same address the DW store used, including
the 16x16 tiling, and an unaligned quad shows the absolute coordinates rather
than tile-local ones. There is no fixed row stride or origin assumption: the
framebuffer and rt3 use a 1024-byte pitch, and the identity holds for both
linear and tiled layouts.

The narrow formats only carry part of the tag, so those variants put one
coordinate in the byte that survives:

| variant | row 0 | reading |
|:--|:--|:--|
| `src-rt5-a8-x` | `01000000` `02000000` ... `40000000` | x+1 in the A byte, all rows identical |
| `src-rt5-a8-y` | row 1 `02000000`, row 63 `40000000` | y+1 in the A byte |
| `src-rt5-l8-x` | `FF010101` `FF020202` ... `FF404040` | x+1 replicated as luminance, alpha 1.0 |
| `src-rt5-l8-y` | row 63 `FF404040` | y+1 |

`src-rt5-rgb565` keeps bytes 0..2 and quantises them: row 0's first four words
are all `FF9C0000`, the last column is `FF9C0042`, and row 63 starts
`FF9C4100`. The 5-bit red loses the low bits of the small coordinates and the
6-bit green rounds up, but the ramp is monotonic in both axes and the digest is
unique. All four formats agree with section 12's channel mapping: a8 keeps the
A byte, l8 keeps R and replicates it, rgb565 keeps R, G, B and replaces alpha.

### Absolute position

The quad was moved with the "offset" uniform and the readback window followed
it, so a quad-relative or window-relative address would show up as a shifted
map instead of an empty one:

| variant | region | row 0 | reading |
|:--|:--|:--|:--|
| `off-32-16` | 32,16,64,64 | `BF9F1121` ... `BF9F1160` | R=0x21 (x=32), G=0x11 (y=16), last column x=95 |
| `off-1-0` | 1,0,63,64 | `BF9F0102` ... `BF9F0140` | starts at x=1, 63 columns, `nz=4032` |

`off-32-16`'s last row is `BF9F5021` ... `BF9F5060`: G=0x50 is y=79, R keeps
the same x range. The tags are absolute window positions and the fetch follows
them.

### The DW's byte conversion

The tag keeps both coordinates below `0x60` because the conversion to a byte is
not a plain `v * 256`. Measured fx10 pattern to stored byte: `0x40 -> 0x40`,
`0x60 -> 0x60`, `0x7F -> 0x7F`, but `0x80 -> 0x7F`, `0x81 -> 0x80`,
`0x83 -> 0x82`, `0xA0 -> 0x9F`, `0xC0 -> 0xBF`. Patterns at or above `0x80`
come back one lower. This was found by the first tag encoding, `2x + 1`, whose
ramp read `... 127, 128, 130, ...` past x=63; it is also why the markers are
`0x9F` and `0xBF`. The rule is only checked for patterns below `0x100`.

### What this settles

On this device and setup, the PSEQ fetch reads the render target named by bits
16..19 at the fragment's own window position, with absolute coordinates, and
the address it uses is the one the DW store used for that surface: tiled or
linear, 4, 2 or 1 byte per pixel, and at an offset quad. The three target
indices tested here (rt1, rt3, rt5) behave the same and the destination pair
bit does not change the address; the enable and index bits themselves are
section 12's result. A store from the previous packet is visible to the fetch.

### What this does not settle

* **Mechanism.** Every test stores to the fragment's own pixel before fetching,
  so "address from the position registers" and "address from the fragment's
  write target" produce the same map. A fragment that fetches without storing
  first - for instance on a second draw over the previous frame's surface - is
  not covered.
* **A 64x64 target.** The harness allocates 256x256, so the height term in
  `posy` and a 256-byte pitch with 4-byte pixels were not exercised. Pitches
  were varied only through the pixel size (1024, 512, 256 bytes).
* **Coordinates past 95.** The tag encoding covers x and y up to 95; larger
  coordinates and the target edges are untested.
* **Layer and alignment fields.** The fetch word's remaining bits were only
  swept in section 12, and not on a position-dependent surface.

## 15. TEX destinations and sampler state

`asm_characterize.tex_sampling.json` (76 variants), template `asm/tex_probe.in`
with constant coordinates, and three harness additions in `tools/assembler.c`:
`GRATE_TEX_CHANNELS` (one channel per texel in row 0, `0x11223344` in row 1),
`GRATE_TEX_MIN_FILTER` and `GRATE_TEX_MAG_FILTER` (filter names, applied after
the `--mipmap` defaults). Every variant fetches with the same instruction word
unless the text says otherwise, stores `r2/r3` or `r0/r1`, and the stored word
is the fetched texel after the DW's byte conversion.

### Component order through both destination pairs

The channel surface paints `0xFF000000`, `0x00FF0000`, `0x0000FF00` and
`0x000000FF` at texels (0..3, 0) and `0x11223344` at (0, 1), so a swap on
either destination path would show up as a different word.

| texel | dest r2/r3 (`0x0420`) | dest r0/r1 (`0x0400`) |
| --- | --- | --- |
| `0xFF000000` | `0xFF000000` | `0xFF000000` |
| `0x00FF0000` | `0x00FF0000` | `0x00FF0000` |
| `0x0000FF00` | `0x0000FF00` | `0x0000FF00` |
| `0x000000FF` | `0x000000FF` | `0x000000FF` |
| `0x11223344` | `0x11223344` | `0x11223344` |

Measured: the destination pair does not reorder the sampled components. Both
pairs carry the four components in the order the surface stores them, in
(r2.lo, r2.hi, r3.lo, r3.hi) and (r0.lo, r0.hi, r1.lo, r1.hi) respectively, so
the pair only selects which registers are written. With the r0/r1 pair the
fetch reads s and t from those same registers and overwrites them; the
operation reads before it writes, which is why the coordinate still took
effect.

### The filter's coordinate convention

`magpoint-*` is the fetch with the default point magnification filter,
`magline-*` the same coordinate with `GRATE_TEX_MAG_FILTER=linear`, both on the
4x4 two-tone surface (texels 0 and 1 black, 2 and 3 white).

| s | point | linear |
| --- | --- | --- |
| 0.0625 | `0x00000000` | `0x40404040` |
| 0.125 | `0x00000000` | `0x00000000` |
| 0.1875 | `0x00000000` | `0x00000000` |
| 0.25 | `0x00000000` | `0x00000000` |
| 0.375 | `0x00000000` | `0x00000000` |
| 0.5 | `0xFFFFFFFF` | `0x80808080` |
| 0.625 | `0xFFFFFFFF` | `0xFFFFFFFF` |
| 0.875 | `0xFFFFFFFF` | `0xFFFFFFFF` |

The linear row fits u = s * 4 - 0.5 with repeat wrap and texel centres at
integer u: at s = 0.0625, u = -0.25 is a quarter of the way from the wrapped
texel 3 (white) into texel 0, giving 0x40; at 0.5, u = 1.5 is the boundary
between texel 1 and texel 2, giving 0x80; 0.625 (u = 2.0) and 0.875 (u = 3.0)
land on texel centres. The alternative u = s * 4 would make 0.375 (u = 1.5) a
half-and-half blend and 0.5 (u = 2.0) a solid white texel; neither is measured.

The point row fits the same centres with edge clamping: at s = 0.0625 the
coordinate sits at u = -0.25, which the point filter resolves to texel 0
(black) rather than to the wrapped texel 3 (white) that the linear filter
includes. Measured: at the same coordinate the point filter clamps outside the
surface and the linear one repeats.

### The same question along t

`magrow-*` samples `GRATE_TEX_ROWCOLOR` (row k is `0x000000FF`, `0x0000FF00`,
`0x00FF0000`, `0xFFFFFFFF`) at s = 0.125 with the linear filter.

| t | word |
| --- | --- |
| 0.0625 | `0x404040FF` |
| 0.125 | `0x000000FF` |
| 0.1875 | `0x000040BF` |
| 0.25 | `0x00008080` |
| 0.375 | `0x0000FF00` |
| 0.625 | `0x00FF0000` |

The same convention holds vertically (v = t * 4 - 0.5): 0.25 is half way
between rows 0 and 1, 0.375 is row 1, 0.625 is row 2. One detail is not
explained: at t = 0.0625 the colour channels show the expected quarter step
toward the wrapped row 3 (R and G `0x40`, B `0xFF`) but alpha is `0xFF` rather
than the `0x40` the same interpolation gives. Every other sampled row has alpha
0 in both sources, so the alpha channel's filtering is only observed at that
wrap edge.

### The mip chain contents

`level-*` reads each level with `nearest-mipmap-nearest` at s = t = 0.125, a
texel centre.

| surface | level 0 | level 1 | level 2 |
| --- | --- | --- | --- |
| ROWCHECK | `0xFFFFFFFF` | `0xFF808080` | `0xFF808080` |
| ROWCOLOR | `0x000000FF` | `0x00008080` | `0x00008080` |
| two-tone, s < 0.5 | `0x00000000` | `0x00545454` | `0x00545454` |
| two-tone, s > 0.5 | `0xFFFFFFFF` | `0xFFD5D5D5` | `0x00545454` |

The opaque surfaces' chains are the 2x2 block averages (ROWCHECK 0.5, ROWCOLOR
the average of two rows). The two-tone's is not: a 2x2 block of its black half
has alpha 0 in all four texels, and the level reads `0x00545454` where the
block average is `0x00000000`; the white half reads `0xFFD5D5D5` where the
block average is `0xFFFFFFFF`. The column boundary is still in the right place.
Measured: this surface's chain is not a plain box filter, and the blends below
are read against these words rather than against the source colours.
Interpretation of the odd value is left open; it does not affect the blend
conclusions because those are stated as fractions of the measured level words.

### Mip level selection and blending

`mip-near-*` uses `nearest-mipmap-nearest`, `mip-lin-*` uses
`nearest-mipmap-linear` (nearest inside a level, blending between levels), with
an explicit LOD from the register (bit 13).

| variant | LOD | surface | word |
| --- | --- | --- | --- |
| `mip-lin-00` | 0.0 | ROWCHECK | `0xFFFFFFFF` |
| `mip-lin-10` | 1.0 | ROWCHECK | `0xFF808080` |
| `mip-near-05` | 0.5 | ROWCHECK | `0xFFFFFFFF` |
| `mip-lin-05` | 0.5 | ROWCHECK | `0xFFC0C0C0` |
| `mip-near-15` | 1.5 | two-tone | `0x00545454` |
| `mip-lin-15` | 1.5 | two-tone | `0x00545454` |
| `mip-lin-20` | 2.0 | two-tone | `0x00545454` |

Measured: the blending filter interpolates the two neighbouring levels
linearly in value (a half of `0xFF` and `0x80` is `0xC0`), and the nearest
filter selects a single level: 0.5 selects level 0, 1.5 selects level 2. Those
two points fit a nearest rule whose ties go to the even level; 2.5 was not
tested. On the two-tone the levels at and above 1 hold the same word, so those
rows show the level content rather than the blend.

### Fractional bias

`bias-*` sends the register through bit 12 instead of bit 13, with the same
blending filter, on ROWCHECK (level 0 `0xFF`, level 1 `0x80`) and on the
two-tone (level 0 `0x00`, level 1 `0x54`).

| register | ROWCHECK | fraction of level 1 |
| --- | --- | --- |
| 1.0 | `0xFFFFFFFF` | 0 |
| 1.25 | `0xFFDFDFDF` | 0.25 |
| 1.5 | `0xFFC0C0C0` | 0.5 |
| 1.75 | `0xFFA0A0A0` | 0.75 |

| register | two-tone | fraction of level 1 |
| --- | --- | --- |
| 1.0 | `0x00000000` | 0 |
| 1.25 | `0x00151515` | 0.25 |
| 1.5 | `0x002A2A2A` | 0.5 |
| 1.75 | `0x003F3F3F` | 0.75 |

Measured: the bias register is added to the estimate with its fractional part
intact, and the levels are then blended linearly; the same register value gives
the same fraction on two surfaces with different level contents. In this
configuration the effective LOD is the register minus one on both surfaces
(0.25 and 0.5 stay at level 0, 1.0 lands on level 1), so the estimate itself is
-1 here. Interpretation: that -1 belongs to the estimate for a constant
coordinate (zero derivatives) and to whatever floor the hardware applies, not
to the bias field, whose effect is the difference between the curves.

### Explicit LOD against the bias register

The `txl-*` sweep on the two-tone with the same blending filter:

| LOD | word | fraction of level 1 |
| --- | --- | --- |
| 0.25 | `0x00151515` | 0.25 |
| 0.5 | `0x002A2A2A` | 0.5 |
| 0.75 | `0x003F3F3F` | 0.75 |
| 1.0 - 2.0 | `0x00545454` | 1 |

Measured: the LOD register is an absolute level, not a bias - 0.25 blends
levels 0 and 1 by a quarter - and the curve is the bias curve shifted by one:
`txl-0p25` and `bias-125` produce the same word. Values at or above 1.0 select
levels 1 and 2, which hold the same word on this surface, so the fraction is
not visible above 1.0.

### The varying path does not reach the fetch

The sampling template first took s and t from an interpolated varying, with a
vertex shader placing the quad and adding a per-variant offset. Every
coordinate-dependent row read as if s = t = 0:

* storing the linked r0/r1 to the surface (`store rt1, r0, r1`, fetch disabled)
  returned `0x00000000` at two coordinates half a texture apart;
* with the point filter, nine different s values from 0.0625 to 0.6875 all
  returned the same texel;
* `filter_quad_vs.txt` driven by an identity `--vs_mat4` also returned zero;
* a fetch in the first exec, where the linked varying is visible to the ALU,
  returned nothing at all, so that layout cannot sample;
* the fetch has to be in a later exec for the sampler to return texels.

Interpretation: in this harness the linked varying is visible to the first
exec's ALU but not to a fetch in a later exec, and a fetch in the first exec
does not sample. That combination, not a property of TEX, is what blocks the
derivative tests below. The two templates were removed and the finding is
recorded here so the next attempt starts from it.

### What this settles

* the destination pair does not reorder the sampled components;
* the linear filter uses u = s * width - 0.5 with texel centres at integer u
  and repeats outside the surface, while the point filter clamps there;
* mip selection picks a single level and mip blending interpolates levels
  linearly, both following the explicit LOD register;
* the bias register is added to the estimate with its fractional part intact
  and shifts the LOD by its value identically on two surfaces.

### What this does not settle

* **Derivative-based LOD.** With constant coordinates the derivatives are zero,
  and the varying path does not reach the fetch, so nothing here separates a
  hardware estimate computed from derivatives from a fixed level.
* **Tie rounding above 1.5.** Only 0.5 and 1.5 were measured with the nearest
  mip filter.
* **The two-tone chain.** The level-1 words (`0x54`, `0xD5`) are not block
  averages; whether that is the harness's mip generation or the surface's alpha
  was not separated.
* **Alpha at the wrap edge.** `magrow-0p0625` reads `0xFF` in alpha where the
  colour channels show a quarter step.
* **Minified sampling with a varying coordinate.** Only magnification was
  sampled with a real coordinate; the minified case is measured with constant
  coordinates and an explicit LOD.

## 16. ALU send ordering and the destination field

`asm_characterize.alu_send.json` (35 variants), template `asm/alu_control.in`.
Packet 0 primes r2 with 0.25 (`0x40`) and r3 with 0.75 (`0xBF`); packet 2 holds
the arrangement under test and stores `rt1, r2, r3`, so the word reads
`[r3.hi][r3.lo][r2.hi][r2.lo]`.

Every arrangement uses the same two instructions and the same destinations:

    MAD  r2.l*,  u2,  #1,  #0 (other)     sends 0.25, writes r2
    MAD  r3.l*,  u0,  #1,  #0 (this)      receives, 0.0625 + accumulator

Only the slots they occupy change. A plain twin without the `(other)` and
`(this)` markers runs at every arrangement too, so the markers are the only
variable between the two halves of the set.

Baselines:

| variant | word | reading |
| --- | --- | --- |
| `primes-only` | `0x00BF0040` | r2 = 0.25, r3 = 0.75, nothing else runs |
| `recv-only` | `0x00100040` | receiver alone: r3 = 0.0625, no accumulator |
| `plain-recv-only` | `0x00100040` | same word without the marker |
| `send-only-s0..s3` | `0x00BF0040` | sender alone in any slot writes r2 = 0.25 and leaves r3 |
| `plain-only-s0..s3` | `0x00BF0040` | identical to `send-only-*` |
| `plain-s0r1` .. `plain-s3r2` | `0x00100040` | every unmarked pair: no transfer |

### Which pairs transfer

`s<i>r<j>` is the sender in slot i and the receiver in slot j; the word is
`0x00500040` (r3 = 0.3125 = 0.0625 + 0.25, sender transferred) or
`0x00100040` (no transfer).

| sender i | j = 0 | j = 1 | j = 2 | j = 3 |
| --- | --- | --- | --- | --- |
| 0 | - | transfer | no | no |
| 1 | transfer | - | transfer | no |
| 2 | transfer | no | - | transfer |
| 3 | transfer | no | transfer | - |

Measured: the transfer set is exactly

    (0,1) (1,0) (1,2) (2,0) (2,3) (3,0) (3,2)

and the non-transfer set is

    (0,2) (0,3) (1,3) (2,1) (3,1)

Every transfer delivers 0.25 - the sender's value - and nothing else changes:
the sender's own destination holds 0.25 in all twelve arrangements, the same as
`send-only-*`, and r3 holds 0.0625 whenever no transfer occurs, the same as
`recv-only`. So in this configuration the send marker changes only the
receiver's accumulator; it does not change what the sender writes.

### What the matrix says and does not say

Three regularities fit every row:

* neighbours inside a pair: (0,1), (1,0), (2,3), (3,2) all transfer;
* the pair boundary forwards: (1,2) transfers, and its reverse (2,1) does not;
* slot 0 receives from every sender: (1,0), (2,0), (3,0).

What does not fit a single lane/pair model is that slot 2 receives from slot 3
and not from slot 1's mirror: (2,1) fails while (3,2) works, and the two extra
receptions into slot 0 have no partner in slot 3 - (0,3) and (1,3) both fail.
Interpretation: the slots behave like two pairs with a forward-only boundary,
and slot 0 has an additional input that any sender can drive. The mechanism is
not established, and no test here separates "slot 0 has a broadcast input" from
"slot 0 is the packet's accumulator sink". The transfer matrix is the measured
part.

### The destination field

The same expression with four destinations produces four instruction words:

| destination | instruction word |
| --- | --- |
| `r0.l*` | `0x00002880` |
| `r1.l*` | `0x0000A880` |
| `r2.l*` | `0x00012880` |
| `r3.l*` | `0x0001A880` |

The register index sits in bits 15 and 16, and the word does not depend on the
slot: `MAD r2.l*, u4, #1, #0` emitted from slot 2 and from slot 3 is the same
`0x00012900` (0.5, u4), and both write r2 (`0x00BF007F`: r2 = 0.5, r3 keeps its
prime). So the mnemonic's destination operand, not the slot position, selects
the register, and any of the four slots can write any of r0..r3. The earlier
`fw-two`/`fw-three` rows already showed two slots writing one register; this
names the field.

The raw-word attempt: an ALU slot accepts a literal. A 64-bit literal is
emitted as two words, and those two words are the slot's instruction word and
the *next* word in the packet (the following slot's control word), not a
standalone instruction. `0x0001290000000000` in slot 2 or slot 3 therefore
runs an instruction assembled from a mix of the literal and the following
control word and stores `0x00BF0000` (r2 cleared), and a zero literal stores
`0x00BF0040` (a no-op, the prime survives). The literal path is a valid way to
*observe* words but not a clean way to inject a chosen instruction; the
destination question is answered from the word dumps above instead.

### What this settles

* the transfer set for one sender and one receiver across all twelve slot
  arrangements, with unmarked controls at every arrangement;
* the sender's own destination is unchanged by the send bit in this
  configuration;
* the destination register is encoded in instruction bits 15-16 and is
  independent of the slot.

### What this does not settle

* **The mechanism** behind the asymmetric transfer set, in particular the extra
  receptions into slot 0 and the (2,1)/(3,2) asymmetry.
* **Two senders into one receiver**: this set has one sender per packet, and
  the §13 multi-sender rows also wrote one destination from several slots, so
  the two effects are not separated.
* **Chaining**: whether a transfer can pass through an intermediate slot was
  not tested with a second receiver.
* **The literal injection path**: a way to place a chosen instruction word
  without disturbing the neighbouring slot was not found.
* **The mixed fp20/fx10 writers and CSEL edge cases** stay where §13 left them.

### Recorded runs

`tests/grate/asm/results/pin-alu-send` and `verify-alu-send` hold 109 rows each
(35 variants, three repeats, plus the four control runs), pinned at
`8996a2094b52...`; re-pinning from the verify directory is byte-identical.

## What the runner cost

Five things that produced wrong results first:

* **an unencodable instruction looks like a hardware result.** The first
  `MUL` sweep used four uniforms and every variant exited 1 with
  `fs: line N: Invalid src register`; the runner records that as `exit-error`,
  not as a result, which is the only reason it was not mistaken for a colour.
  Check the status of the first repeat before reading any word.
* **`expected` has to be pinned from a measured run, not from a guess.** Two
  words were written the wrong way round in this session (`0x007F0040` for
  `0x7F000040`) because the DW byte order was applied from the wrong end. Run
  once with `expected` omitted, read `results.tsv`, then pin: the second run is
  the proof, the first is only a measurement. The reverse also bites - a word
  pinned from a run whose *environment* was wrong is worse than no pin, because
  it turns a generator bug into a failing manifest.
* **a shadowed variable in a generator is a hardware mystery.** Adding a
  `--count` override to `make_alu_buffer_matrix.py` reused the loop variable's
  name, so every variant after the first was poked with the first variant's
  count (4, the size-1 count). Sizes 3 and 4 then returned zero from every store
  for a whole run, and at size 3 they hung, and the first conclusion written
  down was "sizes 3 and 4 are not reproducible". They were: the manifest was.
  The fix is one variable name; the lesson is that when one run disagrees with
  another, check what the manifest *actually asked for* (here:
  `python3 -c 'import json,collections; ...'` over `GRATE_POKE`) before
  concluding that the hardware changed its mind.
* **one hang invalidates the rest of the run, not just itself.** A count that
  leaves an incomplete final group (4 batches at size 3) timed out, and every later variant
  in that run timed out too - including variants that pass on their own in a
  fresh run - because the wedged channel does not recover while the manifest is
  still going. The runner reports those as ordinary failures. Keep known-risky
  variants last, or in their own manifest. After a *killed* run the channel
  needs the kernel's 10 s CDMA timeout per wedged job before anything works
  again, and until then every draw fails with `****nvrm_init failed****` from
  the assembler, which looks like a broken device rather than a wedged one.
* **a uniform-driven probe needs the immediate-operand control in the same
  run.** `fs_alu_immediate_control.txt` is that control (it must read
  `0x000000FF`) and it is a control in all three manifests, next to the shipped
  varying case (`0xFF01FF00`), because a board that has lost the constant path
  returns a plausible `f(0)` instead of an error.
